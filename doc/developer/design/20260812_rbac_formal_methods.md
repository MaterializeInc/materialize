# Formal methods for SQL RBAC

- Associated:
  - Branch: `claude/sql-rbac-formal-methods-79oiky`

## The Problem

Our RBAC implementation is security critical and is verified almost entirely by
example. `src/sql/src/rbac.rs` is roughly 1,950 lines, of which about 1,200 are
a single `match` with one arm per `Plan` variant (81 variants today). That match
is the authorization policy. There is no written specification of it. The code
is the specification, which means:

1. **We cannot review the policy as a policy.** A security reviewer who wants to
   answer "which statements can write to an object the caller does not own" has
   to read 1,200 lines of pattern matching and hold the answer in their head. No
   artifact states the policy in a form that can be checked against intent.

2. **We cannot tell an omission from a decision.** An arm that returns
   `Default::default()` may mean "this statement needs no privileges" or may mean
   "nobody thought about this statement". Both look identical in the source.

3. **The same predicate is implemented more than once, and the copies are only
   claimed to agree.** The authoritative check is `check_object_privileges` in
   Rust. The user-visible answer to the same question comes from the SQL bodies
   generated by the `privilege_fn!` macro in `src/sql/src/func.rs`
   (`has_table_privilege`, `has_schema_privilege`, `has_cluster_privilege`, and
   friends), which route through `pg_has_role`, `mz_aclitem_grantee`, and
   `mz_acl_item_contains_privilege`. Role membership closure is computed a second
   time by `session_role_memberships` in
   `src/adapter/src/optimize/dataflows.rs:790`, which backs
   `mz_session_role_memberships()` and the `mz_show_*_privileges` views. The
   comment on those views states the two are "semantically equivalent to
   `pg_has_role(grantee, 'USAGE')'". That equivalence is a refinement obligation
   between three implementations, and today it is a comment rather than a
   checked property.

4. **Enforcement has multiple entry points and nothing forces them to be used.**
   `rbac::check_plan` is called from `src/adapter/src/coord/sequencer.rs:205` and
   twice from `src/adapter/src/frontend_peek.rs`. `rbac::check_usage` is called
   separately from `src/adapter/src/coord/command_handler.rs:1550`, before
   planning, because purification touches connections and secrets before a plan
   exists. Nothing in the type system requires a new execution path to call any
   of them. The cost of forgetting is a silent, total authorization bypass on
   that path.

The interest in formal methods is well placed, but the phrase "prove the
correctness of our SQL RBAC" needs to be broken apart before it can be acted on.
Some of what we want is provable at low cost with tools already in the tree.
Some of it is not provable at any cost, because it is a statement about intent
rather than about consistency. This document separates the two and proposes a
concrete ladder.

## Success Criteria

- The authorization policy exists as a reviewable artifact, separate from the
  code that implements it, and the two are mechanically checked against each
  other.
- Cross-cutting properties of the policy (monotonicity under `GRANT`, relaxation
  soundness when RBAC is off, uniformity across statement families) are checked
  on every CI run rather than argued in review.
- "This execution path performs an authorization check" is a compile-time
  property, not a convention.
- The claimed agreement between the Rust enforcement path and the SQL visible
  privilege functions is tested, so a divergence fails a build instead of
  surprising a user.
- We can state precisely which properties remain unverified and why, so residual
  risk is known rather than assumed away.

## Out of Scope

- **Proving the absence of information leaks in the query engine.** The
  end-to-end property a customer cares about ("a role cannot observe data it was
  not granted") is an information flow property over the optimizer, the dataflow
  layer, persist, and error messages. RBAC is one conjunct of it. Nothing
  proposed here says anything about, for example, a plan that leaks row contents
  through an error message or through timing.
- **Proving the policy is the policy we want.** No tool can tell us that
  `CREATE MATERIALIZED VIEW` should require `CREATE` on the schema and `CREATE`
  on the cluster. That is a product decision. Formal methods can only check that
  the decision is applied consistently and that the implementation matches what
  we wrote down.
- **Verifying PostgreSQL compatibility as such.** Where we intend to match
  PostgreSQL, differential testing against a real PostgreSQL is the right tool
  and is cheaper than a proof.
- **Verifying authentication**, network policies, and the Frontegg or OIDC paths.
  Those decide who the session's roles are. This document starts from the
  session role metadata and treats it as given.

## Background: the decision procedure as it exists

Formalizing what the code does is a prerequisite for saying what should be
proved, so this section states it precisely. Everything here is read off the
current implementation.

### State

A catalog snapshot `C` provides:

```
Roles     : set of RoleId, always including PUBLIC, mz_system, mz_support
Members   : RoleId -> set of RoleId    -- roles a role is a direct member of
Objects   : set of ObjectId, plus the distinguished SYSTEM pseudo-object
Owner     : ObjectId -> RoleId         -- partial, roles have no owner
Priv      : SystemObjectId -> RoleId -> AclMode
Contains  : item -> schema -> database, and item -> cluster
Default   : DefaultPrivilegeObject -> RoleId -> AclMode
```

`AclMode` is a bitset over `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `USAGE`,
`CREATE`, `CREATEROLE`, `CREATEDB`, `CREATECLUSTER`, `CREATENETWORKPOLICY`.

A session `s` provides `current_role`, `session_role`, `authenticated_role`,
`is_superuser`, `enable_session_rbac_checks`, and `restrict_to_user_objects`.

### Derived relations

Membership closure, as computed by `collect_role_membership`
(`src/adapter/src/catalog/state.rs:978`):

```
holds(C, r) = least set S with r in S,
              and r' in S implies Members(r') subset of S,
              and PUBLIC in S
```

Effective privilege of a role on an object:

```
eff(C, r, o) = union of Priv(o)(g) for g in holds(C, r)
```

### The judgment

`check_plan` computes `C, s |- plan` in three steps.

```
req  = gen(C, plan, current_role(s))         -- generate_rbac_requirements
req' = filter(C, s, req)                     -- filter_requirements
       accept if validate(C, s, req')        -- RbacRequirements::validate
```

`gen` maps a plan to a five-part requirement record: required role memberships,
required object ownerships, required `(object, mode, role)` privilege triples,
the set of catalog item types the statement needs `USAGE` on, and an optional
"superuser only" marker.

`filter` weakens `req` to only its mandatory part when RBAC is disabled for the
session or the session is a superuser. Mandatory means: memberships and
ownerships of system objects only, privilege triples on system objects only with
`SELECT` removed, and no superuser marker.

`validate` is the conjunction of four obligations:

```
U:  for every item i in resolved_ids with item_type(i) in req'.item_usage,
      USAGE in eff(C, current_role, schema_of(i))  and
      USAGE in eff(C, current_role, i)
M:  req'.role_membership subset of holds(C, current_role)
O:  for every o in req'.ownership, Owner(o) in holds(C, current_role)
      (vacuously true when Owner(o) is undefined)
P:  for every (o, m, r) in req'.privileges, m subset of eff(C, r, o)
      (skipped when o is a temporary schema)
```

Note that `P` quantifies over a role `r` carried in the triple, not just the
current role. That is how delegation through views works:
`generate_read_privileges` walks the dependency graph and re-attributes
requirements on a view's inputs to the view's *owner*, following PostgreSQL's
rules-privileges semantics. The traversal is an explicit worklist with a `seen`
set precisely because view chains are user controlled and can be deep.

### Existing machine-checked guarantees

Two properties already hold by construction and are worth naming so we do not
lose them:

- **Plan coverage.** The `match` in `generate_rbac_requirements` has no wildcard
  arm. The final arm is an explicit or-pattern over named variants. Adding a
  `Plan` variant is therefore a compile error until someone writes an arm for
  it. This is a real, if modest, formal guarantee. Introducing a `_ =>` arm would
  silently destroy it, and that is worth a comment in the source and a lint.
- **Membership acyclicity.** `Op::GrantRole` in
  `src/adapter/src/catalog/transact.rs` rejects a grant when
  `collect_role_membership(role_id)` already contains `member_id`, returning
  `CircularRoleMembership`. The check uses the full transitive closure, not just
  direct membership, and it runs inside the catalog transaction. Three readers
  then assume acyclicity, and all three are defensively total anyway
  (`collect_role_membership`, `session_role_memberships`, and
  `generate_read_privileges_inner` all carry visited sets).

## Correctness properties worth verifying

Grouped by what kind of tool can discharge them.

### Class A: properties of the decision procedure alone

These are properties of a pure function from `(C, s, plan)` to a decision. They
are the cheap wins, and they are where a bug would be a genuine defect rather
than a policy disagreement.

**P1 Totality.** For all `C`, `s`, `plan`, `check_plan` returns `Ok` or `Err`
and never panics. This is not obvious. The path contains
`get_privileges(...).expect("only object types with privileges will generate
required privileges")`, the panicking getters `get_item`, `get_role`,
`get_cluster`, and `unreachable!("roles have no owner")` in `ownership_err`. The
requirement generation step and the validation step consult the catalog
separately, and the code already compensates for concurrent drops in some places
(`try_get_role` when formatting membership errors, `retain_items` in
`check_usage`) but not uniformly. A panic here is an availability bug in the
coordinator, reachable by an unprivileged user, so P1 has security relevance
even though it is not a confidentiality property.

**P2 Grant monotonicity.** Define `C <= C'` when `C'` has pointwise larger
`Priv` and `Members`. Then `accept(C, s, plan)` implies `accept(C', s, plan)`,
and conversely a revoke never turns a denial into an acceptance. This catches
inverted set operations, of which the code has several opportunities:
`difference` in the membership check, `remove`/`is_empty` in the mandatory
filter, and the `fold`-with-`union` accumulation in `check_object_privileges`.

**P3 Relaxation soundness.** `filter_to_mandatory_requirements` must weaken,
never strengthen: `validate(C, s, req)` implies `validate(C, s, filter(req))`.
Every superuser session and every session with RBAC off takes this path, so an
error here is high blast radius, and the function is exactly the kind of
hand-written filter where a mistake is invisible on inspection.

**P4 Closure correctness.** `collect_role_membership` computes `holds` as
defined above, terminates on arbitrary input including cyclic input, and always
contains `PUBLIC`. Checking it against a naive fixpoint over the same graph is
straightforward, and it is small enough for bounded model checking.

**P5 Requirement-table uniformity.** These are cross-cutting shape properties of
`gen` over all 81 plan variants. They are the properties that make the policy
auditable, and they are checkable without knowing whether the policy is right:

- every plan that creates a named object in a schema requires `CREATE` on that
  schema.
- every plan that reads a relation requires `SELECT` on it, `USAGE` on its
  schema, and `USAGE` on the target cluster when the plan is not constant.
- every plan that mutates or drops an object requires either ownership of it or
  a named privilege on it, never neither.
- no plan requires a privilege on an object it does not reference. This is the
  least-privilege direction, and the one that produces spurious denials.
- every requirement triple names an object that exists in `C` or is being
  created by the plan.

**P10 Delegation soundness.** `generate_read_privileges` terminates on any
dependency graph, re-attributes exactly the view-owner requirements PostgreSQL
does, and does not lose a requirement when the same item is reached twice by two
different roles. The `seen` set is keyed on `(ObjectId, RoleId)` for that
reason, and the schema-`USAGE` push is guarded by the same set. That interaction
between two uses of one `seen` set is subtle enough to deserve a property.

**P13 Owner privilege invariant.** For every object, `Priv(o)` contains
`owner_privilege(Owner(o))`, preserved by `ALTER ... OWNER TO`, `DROP OWNED`,
and `REVOKE`. This is a catalog state invariant rather than a property of the
decision procedure, but it is what makes ownership meaningful, and it is
maintained by hand in several `transact.rs` arms.

### Class B: agreement between independent implementations

**P6 Predicate agreement.** For all `(role, object, mode)`, the Rust decision in
`check_object_privileges` agrees with `has_*_privilege`, with the
`mz_show_*_privileges` views, and with `mz_session_role_memberships()`.
Divergence in one direction misleads users into thinking they lack access they
have. Divergence in the other direction advertises access that a later
enforcement check denies, which is worse for the MCP data-product views, whose
whole purpose is to tell an agent what it may touch.

**P8 Path agreement.** The coordinator path and the frontend peek path must
reach the same decision for any plan both can handle. They call the same
function, but they assemble its arguments independently, including
`target_cluster_id` and `target_conn_role`, and they resolve the target cluster
through separate code. A fast-path-only acceptance is a privilege escalation.

**P11 Effect ordering.** No externally observable side effect occurs before an
authorization decision that covers it. As stated this property is *false* today,
and deliberately so: purification runs before planning and contacts external
systems using the referenced connections and secrets. What actually holds is
weaker and should be written down. Any pre-plan side effect is preceded by
`check_usage` over `CREATE_ITEM_USAGE` on the pre-plan `resolved_ids`, and
purification only touches items in that set. The second half of that conjunct is
an unverified assumption about `mz_sql::pure::purify_statement`.

### Class C: properties nothing here can discharge

**P7 Chokepoint.** Every plan that takes effect was authorized. This is not a
property of `rbac.rs` at all. It is a property of the call graph, and it is the
one whose violation is most catastrophic and most likely, since it is violated by
adding code rather than by writing wrong code.

**P9 Read-set soundness.** `resolved_ids` over-approximates every catalog object
a statement reads. This is the keystone lemma. `U`, the `restrict_to_user_objects`
restriction, and the view-owner delegation all rest on it, and none of them mean
anything if it fails. It is currently maintained by convention in name
resolution. The existence of the separate `sql_impl_resolved_ids` parameter,
carrying ids discovered inside SQL-implemented function bodies and checked only
against `restrict_to_user_objects`, is evidence that the approximation needed
refining once already.

**P12 Staleness bound.** Authority binds at statement start against a catalog
snapshot. In-flight statements and long-lived `SUBSCRIBE`s continue after a
revoke. The comment in `frontend_peek.rs` states this intent. The question worth
answering formally is not whether this is a bug (it is a choice, and PostgreSQL
makes a similar one) but what the bound is, and whether any interleaving of
`GRANT`, `REVOKE`, `ALTER OWNER`, `DROP OWNED`, and `DROP ROLE` can produce an
outcome outside it.

## Solution Proposal

A four-layer ladder, ordered by value per unit cost. Layers 0 and 1 are the
recommended funded work. Layer 2 is opportunistic. Layer 3 is a timeboxed spike
with a single question to answer.

The ordering is deliberate and is the main recommendation of this document. The
instinct with "formal methods for RBAC" is to reach for a model checker first.
That is the wrong end. The highest-value first step is to write the specification
down at all, and the second is to make the chokepoint a type error. Both are
cheap, both pay off immediately, and both make a later model useful rather than
decorative.

### Layer 0: write the policy down, and make the chokepoint a type error

**0a. A golden dump of the requirement table.** Add a datadriven test that takes
SQL, plans it against a debug catalog, and prints the derived
`RbacRequirements`. `Catalog::with_debug` already supports exactly this shape of
test (see `src/adapter/tests/sql.rs`), so the harness is mostly assembled. The
output file becomes the reviewable statement of the policy:

```
plan-rbac
CREATE MATERIALIZED VIEW mv IN CLUSTER c AS SELECT * FROM t
----
ownership:  []
privileges: [(schema materialize.public, CREATE, u1),
             (cluster c, CREATE, u1)]
item_usage: {Connection, Secret, Type}
membership: []
```

Value out of proportion to cost. A security reviewer reads one file instead of
1,200 lines of `match`. Any change in policy shows up as a diff in a golden file
in the same PR that changes the code, which is where a reviewer can see it. It
also makes P5 mechanically checkable, because the properties can be asserted
over the dumped records.

This requires exposing requirement generation from `mz_sql::rbac`, which is
currently private. Rather than a test-only escape hatch, expose it as a public
description type. That has independent value: the same API can back operator
introspection along the lines of "what would this statement require", which is a
frequent support question.

**0b. Typestate for the chokepoint (P7).** Make the sequencer entry points
accept an `Authorized<Plan>` that only `rbac::check_plan` can construct. A new
execution path then cannot reach a sequencer without a check, because there is no
other way to obtain the token. This turns the highest-consequence failure mode
into a compile error for a few days of work. It is a proof by construction, and
it is worth more than any model of the same property, because a model cannot
observe a call site somebody added last week.

The same technique applies to P11. A capability token minted by `check_usage`
and required by the connection and secret accessors in purification would turn
"purification only touches checked items" from an assumption into a type-level
fact.

### Layer 1: an executable specification with property tests

Write the authorization judgment a second time, declaratively, as a small pure
model: synthetic `Roles`, `Members`, `Priv`, `Owner`, `Contains`, and a direct
transcription of `holds`, `eff`, and the four obligations `U`, `M`, `O`, `P`.
Then implement `SessionCatalog` over the synthetic state and check `rbac.rs`
against the model with `proptest`, which `mz-sql` already depends on directly.

`SessionCatalog` has 68 methods, which sounds prohibitive. It is not. The
RBAC-relevant subset is small, the rest can be `unimplemented!()`, and two
implementations already exist to crib from
(`src/mz-deploy/src/project/compiler/typecheck/catalog.rs` has two).

This discharges P1, P2, P3, P4, P5, P10, and P13. More importantly, the act of
writing the model *is* the specification work. Much of the value arrives at this
step, before any property is checked, because writing the judgment down forces
the questions that the `match` arms let us avoid.

The model also becomes the regression harness for future RBAC work, which is how
it avoids the fate of most verification artifacts. A model that must be updated
to land a feature stays alive. A model in a separate directory does not.

**Scope note.** The model must not be a refactoring of `rbac.rs` into a shared
helper. Two implementations that share code do not cross-check each other. The
model should be written from the intended semantics, ideally by someone other
than the author of the arm being checked.

### Layer 2: bounded model checking on the self-contained kernels

Kani is already used in the tree (`src/ore/src/pool/region.rs`, and the `kani`
cfg is registered in the workspace lints), so the substrate exists. Good targets,
in order:

- `AclMode` algebra: `contains`, `union`, `difference` monotonicity, and
  `all_object_privileges` well-formedness per object type.
- `filter_to_mandatory_requirements` as a weakening (P3), on bounded
  requirement sets.
- `collect_role_membership` (P4) on bounded role graphs, including cyclic ones,
  for termination and closure equality.

These are days of work each, they run unattended, and they cover the parts of
the system where an off-by-one in a bitset would be invisible to review. They do
not scale to anything that touches the real catalog, and we should not try.

### Layer 3: a temporal model, scoped to one question

Reach for TLA+ only after Layers 0 and 1, and only to answer P12: what is the
staleness bound on authority, and can any interleaving of `GRANT`, `REVOKE`,
`ALTER OWNER`, `DROP OWNED`, `DROP ROLE`, and statement execution escape it?
That is a genuinely temporal question about the coordinator's snapshot
discipline, and it is not answerable by any Rust-level tool.

Model the coordinator's catalog transaction boundary, the per-statement snapshot,
and long-lived `SUBSCRIBE`s. Deliberately do not model the policy table. The
model should be small enough to read in one sitting and should answer one
question.

For the *relational* fragment of the state (membership closure, ownership,
containment, default privilege matching order) Alloy is a better fit than TLA+,
because the properties are first-order over a graph and Alloy will produce
minimal counterexamples. If Layer 3 happens, decide between them based on which
question is being asked rather than on which tool is familiar.

### Layer B work: cross-implementation agreement

P6 and P8 do not fit the ladder, because they are differential rather than
deductive, and both are cheap:

- **P6**: extend the sqllogictest suites (`privilege_checks.slt` and friends)
  with a generated cross-check. For a random catalog built by DDL, compare
  `has_table_privilege(role, obj, mode)` against the outcome of the
  corresponding statement actually attempted as that role. This is the property
  the `mz_show_*_privileges` view comments assert and nothing tests.
- **P8**: assert requirement-set equality between the two paths under
  `ci` profile debug assertions. Note the CLAUDE.md rule here: bind the derived
  sets to a `let` outside the assertion, since `debug_assert!` bodies vanish
  under the optimized and release profiles.

### What remains unverified after all of this

Worth stating plainly, because the point of the exercise is to know the residual
risk rather than to feel better about it.

- **P9** stays an assumption. A runtime over-approximation check ("every id
  touched during planning appears in `resolved_ids`") would convert it into a
  tested property, and is probably the single most valuable follow-on after
  Layer 1.
- **Policy intent** stays unverified by construction. Layer 0a makes it
  reviewable, which is the most that is available.
- **Information flow** through error messages, timing, and optimizer behavior is
  untouched.
- The `restrict_to_user_objects` non-interference goals in
  `20260508_restrict_to_user_objects.md` reduce to P9 plus the allow-list
  argument. They are only as strong as P9.

## Minimal Viable Prototype

Layer 0a, on a single statement family, plus one Layer 1 property. Concretely:

1. `src/sql/src/rbac.rs`: expose requirement generation as a public description
   type.
2. `src/adapter/tests/rbac.rs` and `src/adapter/tests/testdata/rbac`: a
   datadriven harness over `Catalog::with_debug` that dumps the requirement
   record for each statement, seeded with the `CREATE` family and the read path.
3. One proptest for P3 (relaxation soundness), which needs no catalog at all,
   only `RbacRequirements` values, and so is the cheapest possible demonstration
   that the approach finds real facts.

That is a small enough slice to build before the design meeting, and it tests the
two claims this document rests on: that the debug catalog makes golden dumps
cheap, and that the requirement records are small enough to be worth reading.

## Alternatives

**Full mechanized proof (Coq, Lean, Verus).** Verify `rbac.rs` itself against a
machine-checked specification. Rejected. The function is parameterized over
`impl SessionCatalog` with 68 methods and reaches into the whole catalog, so the
proof burden is dominated by specifying the catalog rather than the policy. The
cost is person-years and the artifact rots on the first refactor.

**TLA+ or Alloy first.** The instinctive answer, and the one most likely to be
proposed in the meeting. Rejected as a starting point. A model disconnected from
81 policy arms tells us about an idealized RBAC system rather than ours, and the
failure modes we actually have (a missing arm, a forgotten call site, two copies
of a predicate drifting apart) are invisible to it. It becomes worthwhile once
Layer 0 has produced something for it to be checked against, and even then only
for the temporal question.

**Refactor `rbac.rs` into a declarative table and call that the specification.**
Tempting, and it would improve the code. But a single table is a single
implementation. It gives up the cross-check that makes Layer 1 valuable. Worth
doing for readability, not as a substitute for a second implementation.

**Extend parallel-workload to fuzz RBAC.** Complementary and cheap, and it would
find P1 violations in situ, including the concurrent-drop races that a synthetic
catalog will not reproduce. It cannot find P2, P3, or P5, because it has no
oracle. Worth doing alongside Layer 1, not instead of it.

**Differential testing against PostgreSQL.** The right tool for the pg-compat
surface, and it should be part of the P6 work. It says nothing about the parts of
the model that are ours alone (clusters, secrets, connections, network policies,
`mz_support`, `restrict_to_user_objects`), which is where our policy is most
likely to be wrong, since there is no reference implementation to copy.

**Do nothing beyond more sqllogictests.** The honest baseline. The existing
suites (`privilege_checks.slt`, `privilege_grants.slt`, `object_ownership.slt`,
`default_privileges.slt`, `rbac_enabled.slt`, and others) are good and cover the
policy broadly by example. They cannot cover 81 plan variants times the
membership, ownership, and privilege dimensions, and they cannot state a
cross-cutting property at all. Layers 0 and 1 are cheap enough that this
baseline is hard to defend.

## Open questions

1. Who owns the model in Layer 1? It only stays alive if updating it is part of
   landing an RBAC change, which means it needs a named owner and a line in the
   RBAC review checklist.
2. Is exposing requirement generation publicly acceptable, or should Layer 0a
   use a test-only feature gate? The public version has independent value for
   operator introspection, which argues for public.
3. Does P12 have a customer-visible answer today that we are committed to? If
   in-flight `SUBSCRIBE` behavior after `REVOKE` is already documented, Layer 3
   is verifying a commitment rather than discovering one, which changes its
   priority.
4. Should the P8 shadow check be a `ci`-profile assertion or a permanent runtime
   check? A permanent check costs a second requirement generation per statement
   on the fast path, which is the path that exists to be fast.
5. Is there appetite for the capability-token refactor in purification (P11), or
   should that assumption simply be documented and audited by hand? The refactor
   touches purification broadly and is the most invasive change proposed here.
