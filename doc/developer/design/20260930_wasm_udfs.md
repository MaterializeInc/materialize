# WebAssembly user-defined functions

- Associated: (none yet)

## The Problem

Materialize has no user-defined functions. Users who need logic outside the
builtin function set (domain-specific parsing, scoring, hashing, geo math,
custom encodings) have to precompute it upstream, before the data reaches a
source, or write it as long SQL expressions that are hard to test and slow to
plan. Other streaming databases (RisingWave, Databend, SingleStore, ScyllaDB)
let users ship compiled functions as WebAssembly modules and call them from
SQL.

We want the same, with the RisingWave guest ABI and a SQL surface close to
RisingWave's:

```sql
\set wasm_binary `base64 < path/to/udf.wasm | tr -d '\n'`
CREATE WASM MODULE udfs USING BASE64 $1 \bind :wasm_binary \g
CREATE FUNCTION gcd(int, int) RETURNS int LANGUAGE wasm USING MODULE udfs;
SELECT gcd(a, b) FROM t;
```

Two constraints make this harder for Materialize than for a batch database:

1. **Functions must be deterministic.** Differential dataflow retracts a row
   by recomputing it. If `f(x)` returns a different value at retraction time
   than at insertion time, the retraction does not cancel the insertion. This
   leaves negative multiplicities in arrangements, and a single impure UDF can
   make a replica produce wrong answers or crash. Replicas of one cluster must
   also agree with each other. A batch database can trust an `IMMUTABLE`
   label that the user gets wrong, because a wrong answer stays within one
   query. Here it persists in materialized views. So the runtime enforces
   what it can ([Determinism](#determinism)), and the one property it cannot
   enforce, that a row's outcome depends only on that row, is a documented
   contract that `mz udf` checks before deployment
   ([Batch semantics](#batch-semantics)).
2. **Expression evaluation is row-at-a-time.** `SafeMfpPlan::evaluate_inner`
   evaluates one row's datums at a time, inside a timely worker that must not
   block. Crossing into Wasm has a fixed cost per call (instantiation,
   encoding, the call itself), so UDFs are only viable if that cost is spread
   over many rows. Batching therefore has to ship in the first version.

## Success Criteria

- A user can build a function in Rust with the `arrow-udf` crate's
  `#[function]` macro, upload it with `CREATE WASM MODULE`, bind it with
  `CREATE FUNCTION ... LANGUAGE wasm USING MODULE`, and use it in `SELECT`,
  views, indexes, materialized views and subscribes. A module built for
  RisingWave loads unchanged.
- The same module, arguments and Materialize version always produce the same
  result or the same error. This holds across replicas, across restarts,
  between insertion and retraction, and regardless of how rows were grouped
  into batches.
- A misbehaving module (infinite loop, runaway allocation, trap) produces a
  SQL error for the offending row. It never stalls a worker indefinitely,
  exhausts replica memory, or crashes clusterd. When the host itself fails,
  for example by failing to allocate memory a module is allowed, the replica
  restarts rather than recording an outcome that depends on the host.
- A user can reproduce and debug a failing call locally with the `mz` CLI,
  using the same runtime configuration, type mapping, batching and limits as
  the cluster.
- Amortized per-row overhead for a trivial function (`gcd(int, int)`) at full
  batch size is measured and published. The target is under 100 ns per row.
  arrow-udf's own benchmark (15.5 µs per 1024 rows) suggests this is
  achievable.
- Plans without UDFs are not slowed down.

## Out of Scope

- Aggregate functions and table functions. arrow-udf defines a table-function
  ABI (`->>` signatures, `record_batch_iterator_next`), which we can adopt
  later ([Future work](#future-work)).
- Non-deterministic functions, in particular any real access to clocks,
  randomness, the network, the filesystem or environment variables.
- Inline source compilation (RisingWave's `LANGUAGE rust AS $$ ... $$`). That
  requires a compiler toolchain in environmentd, which we do not want.
- Remote or external UDFs (HTTP, Arrow Flight). They cannot be made
  deterministic.
- Loading modules from a URL, S3 or a file path (`USING LINK`). v1 accepts
  only an inline literal.
- Guest languages other than Rust. The ABI works for any language that can
  produce a wasm32 core module and link an Arrow IPC implementation, but only
  Rust has a maintained SDK today.
- Overloads: two user functions with the same name and different argument
  types in one schema.
- UDFs in expressions evaluated outside compute clusters: Kafka sink
  `PARTITION BY`, column `DEFAULT`s, and anything else environmentd or
  storage evaluates. These are rejected at plan time.

## Solution Proposal

In summary:

- **ABI.** Guests implement the `arrow-udf` 3.0 ABI: a wasm32-wasip1 core
  module that exports one function per signature. Each call receives an Arrow
  IPC record batch and returns one. We write our own host rather than using
  `arrow-udf-runtime`, because the host is where determinism and resource
  limits are enforced, and that runtime configures neither.
- **Batching.** A new batched MFP evaluator groups the rows that reach a UDF
  call site, makes one guest call per batch, and resumes per-row evaluation
  with the results. Per-row evaluation order, predicate short-circuiting and
  error semantics are unchanged.
- **Semantics are per row.** The result for a row is defined as the result of
  calling the function on a batch containing only that row, in a fresh
  instance, under the configured limits. Larger batches are an optimization.
  A batch-level failure is resolved by bisecting the batch until every row
  has its own deterministic outcome.
- **Runtime.** A new crate, `mz-wasm-udf`, owns the wasmtime engine
  configuration, the SQL-to-Arrow type mapping, the batch call path and the
  resource limits. clusterd and the `mz` CLI both link it. `mz_expr` depends
  only on a small trait that the crate implements, so neither environmentd
  nor anything else that links `mz_expr` pulls in wasmtime.
- **Catalog and planning.** `CREATE WASM MODULE` creates a module catalog
  item, and `CREATE FUNCTION ... USING MODULE` creates a user `Func` item that
  references it. Both store their `create_sql` like other user items. The
  planner resolves calls to a new `VariadicFunc::Wasm` variant, which carries
  a module hash rather than the module bytes. Calls are never
  constant-folded, so environmentd validates modules but never runs them.
- **Distribution.** The compute controller installs a module on a cluster
  when it ships a dataflow or peek that references the module's hash, and
  withdraws it when nothing there references it anymore. Clusterd compiles a
  module off the worker threads, shares the compiled module across workers
  while it is installed, and keeps it compiled for a while after its last
  withdrawal so that a reinstall does not compile it again.
- **Devex.** `mz udf` subcommands check, call, replay, download and deploy
  modules, and check the batching contract before deploying.

### SQL surface

A module is a catalog object of its own, and functions reference it:

```sql
CREATE WASM MODULE [IF NOT EXISTS] name USING BASE64 { 'base64 text' | $n };
DROP WASM MODULE [IF EXISTS] name [CASCADE | RESTRICT];
SHOW WASM MODULES [FROM schema];
SHOW [REDACTED] CREATE WASM MODULE name;

CREATE FUNCTION [IF NOT EXISTS] name ( [argname] argtype [, ...] )
    RETURNS rettype
    LANGUAGE wasm
    [IMMUTABLE]
    [STRICT | RETURNS NULL ON NULL INPUT | CALLED ON NULL INPUT]
    USING MODULE module_name
    [WITH ( EXPORT = 'export-name', FUEL = <int>, MEMORY = '<size>' )];

DROP FUNCTION [IF EXISTS] name [( argtype [, ...] )] [CASCADE | RESTRICT];
```

Modules and functions are separate objects for four reasons:

- **One copy of the bytes.** A module that exports twenty functions is stored
  once, not once per function. `SHOW CREATE FUNCTION` output is small and can
  be run again as is.
- **Bounded storage.** The module's `create_sql` holds the decoded bytes
  re-encoded as canonical base64, so padding the upload with whitespace does
  not get past `max_wasm_module_size`.
- **One place for access control and lifecycle.** `USAGE` on a module governs
  who can bind functions to it, `DROP WASM MODULE ... RESTRICT` refuses while
  functions use it, and a later blob store or versioning scheme changes one
  object rather than every function.
- **The SQL surface is the part we cannot change after release.** Inline bytes
  could move to a blob store later on the cluster side, but not in SQL.

Uploading:

- `USING BASE64` follows RisingWave. Whitespace in the text is ignored, so
  output of `base64` with or without line wrapping works.
- The parser rejects statement text over 1,000,000 bytes before lexing
  (`MAX_STATEMENT_BATCH_SIZE`). An arrow-udf guest links an Arrow IPC
  implementation, so even a trivial module is over that in base64 (the test
  fixture is 2.3 MB, 3.1 MB encoded). Such modules are sent as a
  text bind parameter instead, `USING BASE64 $1`. They are then bounded by
  `max_wasm_module_size` and by pgwire's 64 MiB frame limit. With psql 16 or
  later:

  ```sql
  \set wasm_binary `base64 < path/to/udf.wasm | tr -d '\n'`
  CREATE WASM MODULE udfs USING BASE64 $1 \bind :wasm_binary \g
  CREATE FUNCTION gcd(int, int) RETURNS int LANGUAGE wasm USING MODULE udfs;
  ```

  The variable is interpolated unquoted. psql passes `:'wasm_binary'` to
  `\bind` with its quotes, and an unquoted value must not contain the line
  breaks some `base64` implementations insert. Clients that interpolate
  parameters on the client side (psycopg2, PHP PDO with emulated prepares)
  send the module inline and hit the statement limit. `mz udf create` does
  the upload for users of the CLI.
- Planning substitutes the parameter into the statement, so the catalog's
  `create_sql` carries the module and re-plans without parameters at boot.
  Boot parses `create_sql` without the size limit.

Binding:

- `EXPORT` names the guest function to bind, which defaults to the SQL
  function's name. The host rebuilds the arrow-udf signature string from
  `EXPORT` and the SQL signature, then looks up the matching export. So one
  module can back several SQL functions, and a SQL name can differ from the
  name used in the guest's `#[function]` attribute.
- `FUEL` and `MEMORY` override the per-call limits, up to ceilings set by
  system variables ([Resource limits](#resource-limits)).
- `IMMUTABLE` is the only volatility allowed. `STABLE` and `VOLATILE` are
  rejected with an error explaining the determinism requirement. Postgres
  defaults an omitted volatility to `VOLATILE`. Here an omitted volatility
  means `IMMUTABLE`, and the stored definition says so explicitly.
- Null handling defaults to `CALLED ON NULL INPUT`, as in Postgres
  ([Nulls](#nulls)).
- A function's stored `create_sql` spells out everything planning would
  otherwise default: `IMMUTABLE`, the null behavior, `EXPORT`, `FUEL` and
  `MEMORY`. Changing a default later therefore never changes an existing
  function.
- `DROP FUNCTION` accepts an argument list, the form migration tools and dbt
  macros emit. It must match the function's signature.
- A function may not share its name with a builtin function. Builtins in
  `mz_catalog` and `pg_catalog` are searched before user schemas, so a user
  function named `left` would be silently shadowed for every unqualified
  call.
- `IF NOT EXISTS` on either statement errors, rather than emitting a notice,
  when an object of that name exists with a different definition. A
  deployment pipeline that ships a fixed module under the old name would
  otherwise believe it succeeded.
- `CREATE OR REPLACE` and `ALTER ... SET MODULE` are not supported. Running
  dataflows are compiled against a specific module, and swapping it
  underneath them would break determinism. To ship a fix, users create a new
  module and function and migrate dependents. `mz-deploy` does not handle
  functions yet. Item versioning, as used by `ALTER TABLE ... ADD COLUMN`,
  could later give an `ALTER FUNCTION ... SET MODULE` that pins existing
  dependents to the old version ([Future work](#future-work)).

All of this is behind a feature flag, `enable_wasm_functions`, declared with
`enable_for_item_parsing: true` so existing modules and functions still load
at boot after the flag is turned off. Per repo policy it defaults off in
production and on in CI via `system_parameter_default`.

Privileges:

- Creating a module needs the `CREATEWASMMODULE` system privilege, in
  addition to `CREATE` on the schema. Loading native-compiled code into
  clusterd, which holds persist and cloud credentials, is a different
  capability from creating tables, so it is not granted to `PUBLIC`. It is
  the analog of Postgres' `USAGE ON LANGUAGE`, expressed as a system
  privilege like `CREATECLUSTER`, since Materialize has no language objects.
- Creating a function needs `CREATE` on the schema and `USAGE` on the module.
- Calling a function needs `USAGE` on its schema, checked for every user
  function a statement names, as for the relations it reads. A view or
  index that calls a function needs it only when it is created, so its
  readers do not. There is no per-function `EXECUTE` privilege yet ([Open
  questions](#open-questions)).
- Functions resolve in their own namespace and cannot be renamed, so
  renaming another object never rewrites a call to a function that happens
  to share its name.

### Guest ABI: arrow-udf 3.0

We adopt the ABI that the [`arrow-udf`](https://github.com/arrow-udf/arrow-udf)
guest crate produces, unchanged. A module is a wasm32-wasip1 core module with
these exports:

| Export | Signature | Purpose |
|---|---|---|
| `ARROWUDF_VERSION_3_<minor>` | static, name only | ABI version. The host accepts exactly 3.0. Upstream defines minor revisions as backward compatible, but a module built against a newer one may rely on behavior this host does not implement, so each new minor version is accepted only once it is tested. |
| `alloc` | `(len: usize, align: usize) -> *mut u8` | Guest allocator. |
| `dealloc` | `(ptr, len, align)` | Guest deallocator. The host never calls it. |
| `arrowudf_<b64(sig)>` | `(ptr, len, out: *mut CSlice) -> i32` | One per scalar function. |
| `memory` | | Linear memory. |

`sig` is `name(t1,t2,...)->ret`, encoded as unpadded base64 over the alphabet
`A-Za-z0-9$_` so that it is a valid symbol. `usize` is `i32` on wasm32, and
`CSlice` is `{ ptr: i32, len: i32 }`.

A call works as follows:

1. The host allocates `len + 8` bytes with `alloc(len + 8, 4)` and writes an
   Arrow IPC *file* containing one record batch at offset 8. The batch has
   one column per argument.
2. The host calls `arrowudf_<sig>(ptr + 8, len, ptr)`. The first 8 bytes of
   the allocation receive the output `CSlice`.
3. A return value of `0` means the slice holds an IPC file with one record
   batch. Column 0 is the result, with one row per input row. An optional
   second column named `error`, of type `Utf8`, holds per-row error messages.
   arrow-udf names the result column after the function, so the host takes
   the result from position 0 and the error column from position 1, and
   only then checks that column 1 is named `error`.
4. A return value of `-1` means the slice holds a UTF-8 error message for the
   whole call.
5. The host copies the output and discards the instance. It does not call
   `dealloc`: every call gets a fresh instance, so freeing buffers in one
   about to be dropped would only spend fuel.

The guest macro generates the per-row loop, so the ABI itself is
batch-shaped. RisingWave's host always sends one input chunk per call. Ours
sends one batch per UDF call site per group of rows
([Batched evaluation](#batched-evaluation)).

Adopting the ABI as-is means RisingWave and Databend modules, the
`#[function("gcd(int, int) -> int")]` macro and its documentation all work
for Materialize. The host is ours, so everything Materialize-specific is
enforced there, not in the guest: determinism, limits, bisection and type
validation.

The ABI has known warts that we either accept or work around:

- Table-function iterators drop errors. This does not affect v1, which is
  scalar only.
- The input is IPC *file* format, which adds a footer and schema per call.
  At 1024 rows this is a small fraction of the cost. A future
  `ARROWUDF_VERSION_3_1` extension could accept IPC stream format, or
  C Data Interface buffers written directly into guest memory, if profiling
  justifies it. That would be a proposal to upstream, not a fork.
- The signature lives in the export name, not in a typed schema. This is
  enough to validate modules at DDL time, since environmentd only has to
  parse export names ([Planning](#catalog-and-planning)).

#### Type mapping

The SQL signature determines the arrow-udf type name used for export lookup
and the Arrow `DataType` used for encoding. The codec (`mz_wasm_udf::codec`)
is separate from `mz_arrow_util`'s COPY TO and Iceberg mapping, because the
representations differ for most non-trivial types: arrow-udf guests expect
`Utf8`, `Binary`, and decimal text where `mz_arrow_util` chooses `LargeUtf8`,
`LargeBinary`, and `Decimal128`, and reading values back needs validation
that file readers do not.

| SQL type | arrow-udf type | Arrow encoding |
|---|---|---|
| `boolean` | `boolean` | `Boolean` |
| `smallint`, `integer`, `bigint` | `int16`, `int32`, `int64` | `Int16`, `Int32`, `Int64` |
| `uint2`, `uint4`, `uint8` | `uint16`, `uint32`, `uint64` | `UInt16`, `UInt32`, `UInt64` |
| `real`, `double precision` | `float32`, `float64` | `Float32`, `Float64` |
| `numeric` | `decimal` | `Utf8`, extension `arrowudf.decimal` |
| `date` | `date32` | `Date32` |
| `time` | `time64` | `Time64(Microsecond)` |
| `timestamp`, `timestamptz` | `timestamp` | `Timestamp(Microsecond, None)`, UTC for `timestamptz` |
| `interval` | `interval` | `Interval(MonthDayNano)` |
| `jsonb` | `json` | `Utf8`, extension `arrowudf.json` |
| `text`, `varchar`, `char` | `string` | `Utf8` |
| `bytea` | `binary` | `Binary` |
| `T list`, one-dimensional `T[]` | `T[]` | `List` |

Notes:

- Numeric crosses as decimal text, which is lossless on the wire, unlike a
  fixed `Decimal128(38, s)`. The guest side narrows it: the arrow-udf Rust SDK
  parses a decimal argument into a `rust_decimal::Decimal`, which holds at
  most 28 significant digits at a scale of at most 28, and panics on anything
  else, including NaN. The host therefore rejects such arguments before the
  call, as an evaluation error for that row, instead of letting one value
  trap the whole batch.
- Arrays cross as plain lists, so their lower bounds cannot come back. An
  array argument with a lower bound other than 1, or with more than one
  dimension, is an evaluation error for that row. SQL array types have no
  dimensions to reject (`int4[][]` is `int4[]`), so a nested arrow-udf list
  must be declared as a SQL list, `int4 list list`.
- `timestamp` and `timestamptz` share one arrow-udf type, so a module's
  export list cannot tell them apart. The SQL declaration decides. `mz udf`
  always presents the type as `timestamp`; a `timestamptz` function is
  declared by hand.
- arrow-udf's `json` arguments reach the guest as `serde_json::Value`, which
  holds numbers as `f64` unless the guest enables `arbitrary_precision`.
- Intervals cross as Arrow's month, day and nanosecond fields. Only the time
  part is scaled from microseconds to nanoseconds, so an interval whose time
  part exceeds about 292 years (months and days aside) overflows on the way
  in, which is an evaluation error for that row. Sub-microsecond parts of
  returned intervals are truncated toward zero.
- Records (arrow-udf `struct` types, declared by `arrowudt_` exports), `uuid`,
  maps, ranges, and types without an arrow-udf name are rejected at `CREATE
  FUNCTION`. Multi-dimensional array values are rejected per row, as above.
- Return types cannot carry type modifiers (`varchar(n)`, `numeric(p, s)`,
  `timestamp(p)`), on the type itself or on array and list elements inside
  it, so a returned value never has to be checked against one.
- Values coming back from the guest are validated: `decimal` and `json` text
  must parse, and dates, times, and timestamps must be in range. A failure is
  an evaluation error for that row, not a panic.

#### Nulls

The arrow-udf macro decides strictness inside the guest: a non-`Option`
parameter makes the generated loop emit `NULL` without calling the user's
code. The host cannot see this from the export name, so it cannot infer
optimizer properties from the binary. Instead:

- `STRICT` (or `RETURNS NULL ON NULL INPUT`) tells both the host and the
  optimizer. The host removes rows with a `NULL` argument from the batch and
  returns `NULL` for them without calling the guest. `propagates_nulls` is
  true.
- `CALLED ON NULL INPUT`, the default, passes `NULL`s to the guest.
  `propagates_nulls` is false.
- `introduces_nulls` is always true, since the guest can return `NULL` for
  any row.

A mismatch between the declaration and the guest is harmless. A `STRICT`
declaration on a guest taking `Option` means the guest never sees `NULL`s,
which is what the declaration says. A `CALLED ON NULL INPUT` declaration on a
strict guest only costs the optimizer information.

#### Errors

A row's call can fail in five ways, and each becomes an
`EvalError::WasmFunction { name, kind, message }` for that row:

- The guest returns a message in the `error` column (the function's `Result`
  was `Err`).
- The call traps: a panic (which aborts under `wasm32-wasip1`),
  `unreachable`, or an out-of-bounds access.
- The call runs out of fuel.
- The call hits the memory limit.
- The guest returns `-1` for the whole call, or output that does not follow
  the ABI.

The last four are batch-level failures. They are attributed to rows by
bisection ([Batch semantics](#batch-semantics)).

Guest output is untrusted input to the host. Before decoding any arrays, the
codec checks the IPC file's framing, declared row count and schema against
the output buffer and the declared return type: the footer and block bounds,
exactly one record batch, no dictionaries, the result type in column 0, and
nothing but an optional `Utf8` error column after it. Decoding requires
aligned buffers. Arrow would otherwise copy each misaligned buffer to
realign it, and since a file's buffers may overlap, a small output could
make the host allocate many times the guest's memory limit. For the same
reason the FlatBuffers verifier runs with limits on depth and on how far
shared tables can expand, and the raw schema is checked for field count,
nesting, name length and metadata before Arrow converts it. Decoding then
uses a schema built from the declared return type, so the guest's field
names and metadata never reach an error message (Arrow prints field
metadata in hash order). A call's output may decode to at most one value per
16 bytes of its memory limit, nested values included: a list of booleans
takes one bit per element in the output but a whole `Datum` on the host.
Exceeding that fails the call, and bisection narrows it to the rows
responsible. Arrow's own decoder still panics on some malformed metadata,
so decoding runs under `catch_unwind`, and a caught panic fails the call
like any other malformed output.

Only failures that come from the guest become errors: traps, fuel and memory
exhaustion, `proc_exit`, and output that breaks the ABI. Anything else, such
as the host failing to map memory for an instance or compiled code, a
compiler panic, module bytes that do not match their hash, or a module that
the controller has not installed, halts the replica instead. Recording it
would persist an outcome that depends on host state rather than the module
and its input.

Every message that carries guest-controlled text, whether the `-1` message,
an `error` column value, a trap's backtrace, captured output or a decoding
diagnostic quoting a returned value, is cut to 4 KiB, and each backtrace
frame name to 256 bytes. Bisection can make one failure into an error on
every row, so an uncapped message would multiply host memory.

Errors flow into persist, so their text must be deterministic. Messages carry
the function's qualified name, the kind, and the guest message or the trap
description with a Wasm backtrace. The backtrace uses function names from the
module's name section and Wasm code offsets, which are properties of the
binary. Messages never include host addresses or timings. The new
`EvalError` variant needs a matching `ProtoEvalError` addition, which is
backward compatible.

#### Imports

arrow-udf modules are `wasm32-wasip1` binaries, so they import
`wasi_snapshot_preview1`. Rust std reaches some of these imports even in pure
code: the default `HashMap` hasher seeds itself from `random_get`. So the host
provides a complete, deterministic preview1 implementation instead of trapping
on use. The implementation is our own (`mz_wasm_udf`'s `wasi` module), about
50 small host functions, rather than `wasmtime-wasi`: that crate's preview1
support pulls in the component model, async runtimes, and capability-based
filesystem access, and every behavior here is a fixed answer that is easier
to audit for determinism when written out:

| Capability | Behavior |
|---|---|
| `random_get` | Deterministic SplitMix64 stream with a fixed seed, reset per instance. |
| `clock_time_get` | Frozen at the Unix epoch. |
| `clock_res_get` | A fixed resolution of 1,000 ns. |
| `poll_oneoff` (sleep) | Returns immediately, reporting every clock subscription as elapsed. |
| `environ_*`, `args_*` | Empty. |
| Filesystem | No preopens, so every path operation and every operation on a descriptor other than 0 to 2 fails with `EBADF`. `fd_fdstat_get` succeeds on descriptors 0 to 2, and `fd_read` on stdin reads zero bytes. |
| `fd_write` on stdout and stderr | Captured, up to 4 KiB in total per guest call ([Logging](#logging)). |
| `proc_exit` | Trap with the exit code. |
| Sockets | Linked, and fail with `ENOTSUP`. |

Every host function checks the pointers and lengths it receives against the
guest's memory before touching anything, and works on guest memory in place
rather than copying it into host buffers. Host allocation therefore stays
bounded by the memory limit whatever a guest passes. Host work is charged as
fuel: every call into the host costs 100 units, about what crossing the
boundary costs in guest instructions, and functions that process guest
memory charge one more unit per byte, so a guest cannot spend unmetered CPU
time in host calls. Wasmtime charges the bulk memory and table operations
(`memory.fill`, `memory.copy` and the like) per byte or element in the same
way, which a test pins, so fuel bounds a guest's CPU time.

The ABI crate lists every preview1 function with its signature, and a test
checks that the runtime's linker defines exactly that list, so validation in
environmentd and linking in clusterd cannot drift apart.

Seeding `random_get` means `HashMap` iteration order inside the guest is
fixed. That is what we want, but it is also a sharp edge for anyone who calls
`rand` expecting randomness. The docs must say so, and `mz udf check` warns
about modules that import `random_get`, `clock_time_get` or `poll_oneoff`.
Any import outside `wasi_snapshot_preview1` fails `CREATE WASM MODULE`.

### Batched evaluation

#### The batched evaluator

MFP evaluation has a batch entry point, `SafeMfpPlan::evaluate_batch`, which
compute's `Mfp` operator and the persist source call. It reads input rows by
index, borrowed from the operator's input containers or a part's decoded
rows, and reports each row's outcome and datums to a callback in row order.
A plan without UDF calls is evaluated a column at a time when every
expression has a typed kernel, and per row otherwise
([Columnar scalar evaluation](#columnar-scalar-evaluation)). For a plan that
calls UDFs,
`evaluate_batch` uses the evaluator in `mz_expr::linear::wasm`, the batched
counterpart to `SafeMfpPlan::evaluate_inner`. It takes a batch of input rows,
holds a datum vector per row in one arena that lives for the batch, and walks
the MFP's steps (each mapped expression and each predicate) in the order
`evaluate_inner` uses. For each step it *precomputes and replays*:

1. Find every UDF call in the step, in any position, innermost first.
2. For each call, evaluate its arguments on every live row, and make one
   batch call through the `WasmInvoker` trait for the rows whose arguments
   evaluated. Record each row's outcome (the value, the guest's error, or
   the error its arguments raised) in a thread-local replay frame. Nested
   calls inside the arguments replay outcomes recorded earlier in this step.
3. Evaluate the step per row, exactly as `evaluate_inner` would. When
   evaluation reaches a UDF call, `WasmFunc::eval` returns the row's recorded
   outcome instead of calling the guest.
4. Push each row's datum, drop rows a predicate rejects, finalize rows that
   error, and move on to the next step with the rows still live.

A call replays the outcome it would have computed, at the point where
per-row evaluation reaches it, so every row's result is identical to the
per-row evaluator's. That includes which of several errors a row reports, and
short-circuiting in `If`, `COALESCE`, `AND` and `OR`, so calls in lazy
positions batch like any other. Rows a predicate rejected, or that already
failed, are not sent to the guest. The cost is that a call in a lazy position
also runs on live rows that will not take its branch. Those outcomes are
discarded, so they cost guest work and possibly bisection, but cannot change
a result. A guest that loops on rows its guard excludes pays a full fuel
budget for each batch containing one, plus bisection, and a host failure on
such a row halts the replica although per-row evaluation would never call
the guest for it. Guards are therefore not a way to protect a guest from
inputs it cannot handle: the guest must handle every input of its declared
types. Restricting the guest to live rows matters more for a UDF than for
a builtin: a guest call is expensive, and rows the plan has already
eliminated could still exhaust its fuel and force bisection.

A batch holds its input rows, its output rows, and an arena with every value
its evaluation produces until the batch is emitted, including guest results
that a later predicate discards, so a batch's host memory is not bounded by
any one call's limits. Both sites size their batches with `MfpBatchSizer`
from all three: batches start at 64 rows, double while a full batch stays
under half of 64 MiB, and after a batch over 64 MiB shrink to half the
target's worth of rows at that batch's bytes per row. Input rows alone end a
batch early once they reach the target. Grouping cannot change results, so
this bounds host memory near the target without a nondeterministic budget
error. A sudden jump in row sizes can overshoot the target once before the
size adapts. Guest error messages, which the replay frame also holds, are
capped at 4 KiB each ([Errors](#errors)). The compute operator lends rows
from its input containers instead of copying them, evaluates once it holds a
batch's worth of rows, emits each batch's outputs as soon as the batch is
evaluated, and then releases the containers.

Call sites are identified by the address of their `WasmFunc` within the plan,
which does not move while a batch is evaluated. A frame is installed for the
duration of one `evaluate_batch` call and removed by its guard, so per-row
evaluation outside a batch, including a panic unwinding through one, sees no
frame and calls the guest directly.

Both sites batch any plan that calls a UDF, even when batched evaluation is
otherwise off (`enable_compute_batched_mfp`, `storage_source_batched_mfp`,
both off in production and on in CI). A plan without UDF calls keeps the
per-row path unless those flags are on.

#### Batch sizes and vectorized guests

The ABI is batch-shaped, and so is the guest side of it. One guest call
carries a whole Arrow batch, and the guest decides how to process it:

- The `#[function]` macro's generated export loops over rows inside the
  guest, so even a scalar Rust function crosses the boundary once per batch.
- For functions whose arguments and result are primitive numbers, the macro
  generates SIMD kernels over whole arrays.
- `#[function("...", batch_fn = "f")]` hands `f` the input columns as Arrow
  arrays and takes its output column back, so the guest can use Arrow compute
  kernels or any other vectorized code. The fixture's `saxpy` is an example.

For this to pay off, batches must be large. Compute batches rows across the
containers that arrive in one operator activation (`flat_map_rows_batched`),
and the persist source batches decoded rows. Both cap a batch at 16K rows
(`compute_mfp_batch_rows` in compute when batched evaluation is on) and size
it below that by its memory ([Batched evaluation](#batched-evaluation)).
The invoker splits a call further only at `wasm_udf_batch_max_rows` rows
(default 16K) and `wasm_udf_batch_max_bytes` (default 8 MB), both
replica-scoped dyncfgs. The byte limit is a target against an estimate of
each row's encoded size, not a cap: a call always carries at least one row,
so a single row larger than the target still makes its own call. A test checks that ten thousand rows
reach a `batch_fn` guest in one call.

#### Where MFPs are evaluated

| Site | Batching |
|---|---|
| `Mfp` render over collections and arrangements (`render/context.rs`) | Batched over each activation's input. MFPs that seek to a literal key value stay on the fused per-row arrangement path. |
| Source imports (`persist_source`) | Batched inside the source's decode operator, over up to 16K decoded rows of a part at a time, bounded by the decode fuel. The MFP stays pushed down, so persist filter pushdown and its audit apply as usual. |
| Arrangement keys (`arrange_collection`), so index keys and join keys | Per row. |
| Temporal bounds (calls inside `mz_now()` comparisons) | Per row, after the batched maps and filters. A plan whose only call is in a temporal bound is not batched at all. |
| `Reduce` key and value plans | Per row. |
| MFP after a table function | Per row. |
| Peek result iteration | Per row. |
| Join closures | Per row. |

The per-row sites are correct but slow. A call there pays the whole fixed
cost of a guest call for one row, about 30 µs, against 50 to 450 ns per row
in a full batch, and users do not control where the optimizer places a
call. We accept that for v1 rather than rejecting plans with calls in those
positions, and batch the remaining sites as follow-up work
([Future work](#future-work)). The user docs should name the slow positions
(`GROUP BY` and index or join keys computed by a function) so that users can
compute the value in a preceding view instead. `MfpPlan`'s temporal bounds
(`mz_now()` filters) are evaluated per row after the batched stages.

#### The `WasmInvoker` boundary

`mz_expr` must not depend on wasmtime. Everything that links `mz_expr`,
environmentd included, would otherwise pull in Cranelift. `WasmFunc`
therefore carries a handle to an object implementing a trait defined in
`mz_expr`:

```rust
pub trait WasmInvoker: Send + Sync + Debug {
    /// Calls the function on each row of `args` and returns one result per
    /// row, in order. The outcome for a row does not depend on the other
    /// rows in the batch.
    fn call_batch<'a>(
        &self,
        args: &[&[Datum<'a>]],
        arena: &'a RowArena,
        out: &mut Vec<Result<Datum<'a>, EvalError>>,
    );
}
```

`mz-wasm-udf` implements it. A process that evaluates UDFs installs a
process-wide `WasmRuntime` (`mz_expr::func::install_wasm_runtime`), and each
`WasmFunc` binds itself to an invoker from it on first use, caching the
binding in a cell that is not part of its identity. The scalar `eval` path,
which is the per-row fallback, calls `call_batch` with one row. Evaluating a
`WasmFunc` in a process without a runtime, which in practice is environmentd
evaluating a constant expression, is an `EvalError::Unsupported` saying the
function only runs in a query on a cluster ([Catalog and
planning](#catalog-and-planning)). Binding a function whose module the replica
does not have installed halts the replica, as a host failure does
([Errors](#errors)): the controller installs every module before what calls
it, so a missing module is a bug, and a restarted replica reconciles and
receives every module it needs.

### Batch semantics

Batching rests on one contract between the host and the guest:

> A function's outcome for a row (value or error) depends only on that row's
> arguments.

Given the contract, the outcome for a row is the outcome of calling the
function on a batch containing only that row, in a fresh instance, with the
function's fuel and memory limits. The host makes every observed outcome
match that definition:

- **Fresh instance per batch.** Each batch runs in a newly instantiated
  module, created from a pre-linked `InstancePre` with copy-on-write memory
  images. No state survives between batches.
- **Per-row errors are final.** An entry in the `error` column is the guest's
  answer for that row.
- **Batch-level failures bisect.** If a batch traps, runs out of fuel, hits
  the memory limit or returns `-1`, the host splits it in half and retries
  each half in a fresh instance, down to single rows. A single-row failure is
  that row's error. Rows in halves that succeed get their values.
- **One limit for all batch sizes.** Fuel and memory limits apply to every
  call, whatever its size. A batch that completes within the limits proves
  that each of its rows would complete alone, provided the cost of a row
  alone is no greater than the cost of any batch containing it. That holds
  whenever rows do not affect each other's work, and also for per-instance
  caches, because the batch pays for warming the cache itself. So a cheap
  function runs at full batch size, and a heavy one converges to batches of
  about `limit / cost_per_row` rows. The host keeps a per-function estimate
  of fuel per row and sizes the next batch from it. Batch sizing never
  changes results, so the estimate does not need to be deterministic.

So the contract has a second half, about cost:

> Computing a row alone costs no more fuel and memory than computing any
> batch that contains it.

A `batch_fn` guest can break it while computing exactly the right values:
one that switches to a cheaper algorithm for large batches might finish a
large batch within the limits and run out of fuel on a single row. An
insertion in a large batch then succeeds and its retraction, alone, fails.
`batch_fn` stays supported, and the user docs state the cost half of the
contract next to it.

The host cannot enforce the contract itself, so it is trusted, the way
Postgres trusts `IMMUTABLE`. A fresh instance per batch removes state between
batches but not between the rows of one batch, and guests can leak state
across rows without meaning to. Rust's standard library is enough: each
`HashMap` or `HashSet` an instance builds gets the next hash key, so a
function that returns elements in hash iteration order gives identical rows
different results at different positions in a batch. Seeded randomness from
`random_get`, counters and caches keyed on more than the arguments do the
same. A violation leaves retractions that do not cancel their insertions in
the dataflows that use the function ([The Problem](#the-problem)). Running
every row in its own instance would rule this out, but costs about 30 µs per
row ([Alternatives](#alternatives)).

Instead, the contract is checked before a function reaches a region.
`mz udf create` generates 16,384 argument rows from the declared types and
runs them in one batch, one row per call, in batches of seven, and in
reverse order. It compares typed outcomes, so a `NULL` result differs from
the string `'NULL'`. It refuses to create the function if any row's outcome
differs, or if no row the guest was called on succeeds, since rows that fail
the same way everywhere, or never reach the guest, agree without showing
anything. `--skip-check` overrides it. The rows come from a fixed seed and
mix small values, each type's edge cases, `NULL`s (unless the function is
`STRICT`) and repeats of earlier rows. 16,384 is the default
`wasm_udf_batch_max_rows`, so the one-batch run reaches the largest batch a
region sends, where a `batch_fn` guest may take a different path than for a
few rows. `mz udf check
--determinism` runs the same check, on generated rows or on a CSV file of
real inputs ([Developer experience](#developer-experience)). The check is a
test, not a proof. It catches leaks that show up on ordinary inputs, such as
hash order, counters and seeded randomness, and misses ones that only
specific inputs trigger. A plain SQL `CREATE FUNCTION` is not checked
([Open questions](#open-questions)).

Bisection is cheap when few rows fail: a single failing row in a batch of
`N` costs about `2 log2(N)` extra calls. In the worst case, when every row
causes a batch-level failure, it makes `2N - 1` calls, each with a fresh
fuel allowance, all on the worker that evaluates the batch. A 16K-row batch
of a function that traps on every row therefore makes 32,767 calls. Fuel
bounds each call, not the evaluation, so such a function can hold a worker
for a long time. A function that errors on a large fraction of rows through
traps rather than through its `error` column runs much slower than one that
returns `Err`, and the docs should recommend returning `Result`. Yielding
between bisection steps is future work.

### Determinism

Wasm is deterministic apart from a short list of documented exceptions. The
engine configuration closes each one, and `mz-wasm-udf` owns that
configuration as a single constant shared by clusterd and the CLI.

| Source of nondeterminism | Mitigation |
|---|---|
| NaN bit patterns | `cranelift_nan_canonicalization(true)` |
| Relaxed SIMD | `wasm_relaxed_simd(false)` |
| Threads, shared memory | Rejected by validation, and not built into the engine |
| Host capabilities | Deterministic preview1 context ([Imports](#imports)) |
| Wall-clock timeouts | Fuel only, no epoch interruption ([Resource limits](#resource-limits)) |
| State carried between calls | A fresh instance per batch ([Batch semantics](#batch-semantics)) |
| Batch composition | Per-row semantics with bisection, for guests that keep the contract, which `mz udf create` checks ([Batch semantics](#batch-semantics)) |
| Stack depth | Fixed `max_wasm_stack`, and code generated for a fixed CPU feature baseline (x86-64-v2 on x86-64, the target defaults on aarch64) rather than for the host's features, so frame sizes, and with them the depth at which recursion traps, are the same on every replica of an architecture. The call runs on enough native stack that deep recursion traps rather than overflowing the host thread. |
| Host failures | Every limit the guest observes depends only on the module and its configured limits. Any failure that does not come from the guest halts the replica instead of producing an outcome ([Errors](#errors)), so a host failure never becomes a persisted row error. |

Fuel accounting and stack-overflow depth can differ between wasmtime
versions, so a row that runs out of fuel on one Materialize version might
succeed on the next. This is acceptable. Dataflows are rebuilt on restart,
and materialized view sinks correct their output against persist, so a
version change produces corrections rather than stuck retractions. It is the
same situation as a bug fix to a builtin function. During a zero-downtime
upgrade the new version runs in read-only mode until cutover, so the two
versions never write the same shard.

### Resource limits

| Limit | Mechanism | Default | Ceiling (system var) |
|---|---|---|---|
| Instructions per call | wasmtime fuel, plus host work in WASI calls ([Imports](#imports)) | 100M | `max_wasm_function_fuel` |
| Linear memory per instance | A `ResourceLimiter` that fails the call when the instance's memory, in total, grows past the limit | 64 MiB | `max_wasm_function_memory` |
| Table elements per instance | The same limiter, which fails the call when the instance's tables, in total, grow past the limit | 1M | none |
| Module size | Checked when `CREATE WASM MODULE` is sequenced | 8 MB | `max_wasm_module_size` |
| Modules per region | Checked when `CREATE WASM MODULE` is sequenced | 16 | `max_wasm_modules` |
| Stack | `max_wasm_stack`, with the call run on enough native stack that deep recursion traps rather than overflowing the host thread | 512 KiB | none |

Validation accepts an explicit allowlist of Wasm features: those the Rust
`wasm32-wasip1` target enables by default, plus fixed-width SIMD. A test
checks that the engine compiles what validation accepts. Multiple memories
are left out because each memory reserves its own host address space, which
the memory limit does not bound, and `externref` because this wasmtime build
has no GC support.

The ceilings are checked when a new module or function is created, not when
its statement is planned, so that lowering a ceiling never stops existing
objects from being re-planned at boot. A `CREATE ... IF NOT EXISTS` whose
object exists with the same definition is a no-op before any of these
checks, so redeploying unchanged objects never fails a limit.

A limit applies to a whole call, not a row. That is what makes the
bisection argument work, so the defaults are sized for a full batch rather
than for one row: 100M fuel leaves about 6K instructions per row at the
default maximum of 16K rows, and the invoker sizes later batches of heavier
functions from the fuel recent calls used per row. 64 MiB covers the input
and output IPC buffers of an 8 MB batch plus working memory. Fuel is
deterministic, so exhausting it is an ordinary deterministic error. We do
not use epoch interruption: it depends on wall-clock time, so it cannot be a
query error. Calibrating fuel against wall time, so that a call at the fuel
ceiling holds a worker for tens of milliseconds at most, is part of the
benchmarking work.

Instances use wasmtime's on-demand allocator with copy-on-write memory
images, not the pooling allocator. A pool has a fixed number of slots, and a
call that found the pool exhausted would fail for reasons unrelated to its
row, which is a nondeterministic error. Wasm memory is not tracked by the
replica's memory accounting. At 64 MiB per concurrent call the worst case is
small next to replica sizes, but the introspection work in
[Future work](#future-work) should report it.

### Catalog and planning

**Parser.** Add `Statement::CreateWasmModule` and `Statement::CreateFunction`
with the grammar above, `SHOW WASM MODULES`, and `SHOW [REDACTED] CREATE
WASM MODULE` and `SHOW [REDACTED] CREATE FUNCTION`. `WASM MODULE` is a new
`ObjectType`, so it works with `DROP`, `ALTER ... RENAME`, `ALTER ... OWNER
TO`, `GRANT USAGE ON`, `COMMENT ON` and default privileges like other items.

**Planning a module.** At creation, `CREATE WASM MODULE`:

1. Decodes the base64, ignoring whitespace.
2. Validates the module with `wasmparser` (decode and validate only, no
   compilation), checks for exactly the `ARROWUDF_VERSION_3_0` export,
   decodes every `arrowudf_*` export into a signature, and checks the
   imports against `wasi_snapshot_preview1`.
3. Computes the module's SHA-256.
4. Writes `create_sql` with the decoded bytes re-encoded as canonical base64.

At boot, re-planning a module from `create_sql` only decodes and hashes it.
Validation runs at sequencing, like the size and limit checks, so that a
stricter validator, a changed `wasmparser` feature set or a dropped ABI
version never stops environmentd from opening an existing catalog.

**Planning a function.** Planning `CREATE FUNCTION` resolves the module by
name, which records its id in the function's `ResolvedIds`, and maps the SQL
signature to an arrow-udf signature string. `create_sql` names the module by
id and spells out every defaulted option. Sequencing then checks what may
change between releases, so that boot, which only re-plans, never depends on
it: that the module exports the signature (on a mismatch, the error lists
the signatures it does export), that the name is not a builtin function's,
and the fuel and memory ceilings. A later release that adds a builtin of the
same name as an existing function therefore does not stop the catalog from
opening.

environmentd never compiles or runs modules.

**Catalog items.** `CatalogItem::WasmModule` holds `create_sql`, the hash and
the decoded bytes. `CatalogItem::Func` wraps a `Func` whose definition is an
enum, `FuncDef::Builtin(&'static mz_sql::func::Func)` or
`FuncDef::Wasm(WasmFunction)`. The WebAssembly arm holds `create_sql`, its
resolved ids (the argument types and the module), and the planned signature,
null behavior, limits, module hash and export name. A function's dependency
on its module is an ordinary item reference, so `DROP WASM MODULE ...
RESTRICT` refuses while functions use it, and every object that calls a
function, including an index whose key does, blocks `DROP FUNCTION ...
RESTRICT`.

Functions resolve in their own namespace, so a function may share its name
with its module or a table. The durable catalog's uniqueness check follows
that: a function conflicts only with another function of the same name.
Functions count toward `max_objects_per_schema` like other items.

`CatalogItemType::WasmModule` is a new durable enum variant, so the change
needs a catalog version bump. The upgrade step only adds variants and
rewrites nothing.

Renaming a schema rewrites the schema name in every module's and function's
`create_sql`. Renaming a module rewrites its name in the functions that
reference it, although resolution at boot is by id.

**Resolution.** `resolve_func` goes through `CatalogItem::func()`, which
returns `&'static Func`. User functions get a separate accessor, and
`plan_function` branches on it. `mz_catalog` and `pg_catalog` are searched
before user schemas unless they appear explicitly in `search_path`, which
is why a user function cannot take a builtin's name. Resolution picks the
first schema with a function of that name and then checks the arguments.
Postgres instead considers every visible function of that name across
schemas. Without overloads, the difference only shows when two schemas on
the search path define a function of the same name with different argument
types.

**Expression.** A new `VariadicFunc::Wasm(WasmFunc)` variant:

```rust
pub struct WasmFunc {
    /// Fully qualified name at plan time. Used only for display and error
    /// messages.
    pub name: String,
    pub module: WasmModuleHash,
    /// The arrow-udf export that implements the call.
    pub export: String,
    pub arg_types: Vec<SqlScalarType>,
    pub return_type: SqlScalarType,
    pub strict: bool,
    pub limits: WasmLimits,
    /// Bound on first use. Not serialized, and not part of `Eq`, `Ord` or
    /// `Hash`.
    pub invoker: InvokerCell,
}
```

It carries the hash, not the bytes, so plans, `EXPLAIN` output and the
LIR-stable format stay small. It follows the `Regex` precedent: `Hash`, `Eq`
and `Ord` cover the serialized fields only. The properties are:

- `could_error`: always true.
- `is_monotone`: false. Persist filter pushdown's abstract interpretation
  treats the result as unknown and never evaluates the call.
- `propagates_nulls`: equal to `strict`.
- `introduces_nulls`: true.
- `output_type`: the declared return type.

The new variant is added to the LIR schema snapshot and to the function
registry, with a `Sample`, as the pinned LIR design requires.

**No constant folding.** `MirScalarExpr::reduce` and `FoldConstants` evaluate
calls whose arguments are all literals, in environmentd. `reduce` skips
`Wasm` calls, and `FoldConstants` checks `contains_unfoldable`, which is true
for unmaterializable and `Wasm` calls alike. Unlike the unmaterializable
mechanism, this does not stop the expression from being rendered in a
dataflow. With no folding:

- `SELECT gcd(4, 6)` becomes a Map over a Constant. It plans as a slow-path
  peek and runs on the cluster, like any non-constant query.
- `INSERT ... VALUES (gcd(1, 2))` and `UPDATE ... SET a = gcd(a, b)` take the
  existing read-then-write path.

**Rejected contexts.** A call runs only where the expression is rendered in
a compute dataflow or a compute peek. environmentd has no runtime, so:

- Webhook `CHECK` expressions, Kafka sink `PARTITION BY` and column `DEFAULT`
  expressions reject calls at planning.
- Sites that require a constant after reduction (`LIMIT`, `OFFSET`, `AS OF`,
  `REFRESH AT`) reject a call as non-constant.
- Sites that evaluate a constant expression directly (`EXECUTE` parameters,
  secret values, side-effecting function arguments, `COPY` options) fail
  with an error saying the function cannot be called outside a query that
  runs on a cluster.

### Module distribution

Clusters need the module bytes. A content-addressed compute command,
`ComputeCommand::InstallWasmModule(WasmModule { hash, bytes })`, delivers
them, and `ComputeCommand::DropWasmModule(hash)` withdraws them.

- The coordinator registers every module with the compute controller when
  it is created, and deregisters it when it is dropped. At bootstrap it
  registers every module before shipping any dataflow: bootstrap ships an
  index right after the object it is on, not after the functions its key
  calls. The controller holds registered modules, but sends none of them
  anywhere eagerly.
- When the controller ships a dataflow or a peek to an instance, it collects
  the module hashes the plan's expressions reference and installs any the
  instance lacks, ahead of the dataflow or peek. A module therefore reaches
  only the clusters whose dataflows or peeks use it, and creating a module
  that nothing calls costs no cluster any work.
- Commands to a replica are ordered, so a module always arrives before the
  dataflow or peek that references it. Command history compaction keeps
  every install not yet matched by a drop, ahead of the dataflows and
  peeks, so reconnecting replicas get the modules they need, first. Each
  worker holds at most one install per module, so a replayed install is a
  no-op, and reconciliation drops the modules a worker holds that the new
  history no longer installs.
- When the last dataflow or peek on an instance that references a module
  goes away, the controller sends `DropWasmModule`. Peek evaluation that
  runs off the worker thread can outlive its peek briefly after a
  cancellation, so it holds pins on its modules until it stops.
- A module with no installs left stays compiled for reuse, so a query that
  is a module's only user does not compile it again on every run. The
  retained modules are bounded at 64 modules and 256 MiB, estimated from
  each module's bytes, its compiled artifact and a fixed overhead per
  module, evicting the least recently released first.

Dataflow descriptions and peeks carry only hashes, so neither changes shape.

On the cluster, every worker receives the install command, and the
process-wide runtime starts compiling the module on a background thread
into an `InstancePre` with the deterministic WASI context linked. Workers do
not wait for it. A worker that binds a function whose module is still
compiling blocks only then, so installing a module never stalls a worker
that does not use it. A module the engine's own validator rejects is
recorded as failed, and every call to a function that uses it fails with a
deterministic error naming the rejection. Validation in environmentd uses
the same features, so that should not happen. Any other compile failure
halts the replica, since it cannot be told apart from the host failing: a
cranelift code-generation limit is a property of the module, but wasmtime
does not report it with a type of its own. A module that hits one therefore
halts every replica that installs it until the module is dropped.

### Storing the module

A module's bytes live base64-encoded in its `create_sql`, in the durable
catalog. That is simple, keeps boot re-planning uniform, and makes `SHOW
CREATE WASM MODULE` round-trip. Every catalog snapshot at boot carries every
module, which is why the size cap exists, and every builtin view over
`mz_catalog_raw` parses each module's `create_sql` on `mz_catalog_server`.
A release-mode arrow-udf module with arrow-rs linked in, after `wasm-tools
strip`, is typically hundreds of KB to a few MB, so 8 MB leaves headroom. A
separate blob store with a content hash in `create_sql` is future work. With
modules as their own objects, it changes only the module item.

`mz_catalog.mz_wasm_modules` has a row per module (id, name, schema, owner,
privileges, hash and size), and `mz_catalog.mz_functions` has a row per user
function. `CREATE WASM MODULE` is a sensitive statement kind, so statement
logging records its redacted form, in which the module is `'<REDACTED>'`,
and redacts its bind parameters, so megabytes of base64 never land in
`mz_statement_history`.

### Logging

Output the guest writes to stdout and stderr cannot affect results, so it is
safe to capture. It can echo row data, though, so on a cluster the replica
logs only its length, at `debug` level. A trap's error keeps the start of
the output, since a Rust guest's panic message is there, cut to 4 KiB like
every guest-supplied message in a persisted error. In the CLI the output is
printed inline. Local reproduction is the main way to debug a function, and
exposing guest output from clusters is future work.

### Developer experience

#### Building a function

The guest side is plain arrow-udf:

A crate with `arrow-udf` as a dependency and `crate-type = ["cdylib"]`:

```sh
cargo build --release --target wasm32-wasip1
mz udf check target/wasm32-wasip1/release/gcd.wasm
```

```rust
use arrow_udf::function;

#[function("gcd(int, int) -> int")]
fn gcd(mut a: i32, mut b: i32) -> i32 {
    while b != 0 {
        (a, b) = (b, a % b);
    }
    a.abs()
}

#[function("safe_div(bigint, bigint) -> bigint")]
fn safe_div(a: i64, b: i64) -> Result<i64, String> {
    a.checked_div(b).ok_or_else(|| "division by zero".into())
}
```

A `mz udf new` scaffold that pins an arrow-udf version the host is tested
against, sets `panic = "abort"` and `opt-level = "s"`, and adds a
`wasm-tools strip` step is future work.

#### `mz udf`

All subcommands link `mz-wasm-udf`, so type mapping, the WASI context,
batching, bisection, fuel and memory accounting are the cluster's code. They
match a region's behavior for the same limits: the CLI takes fuel, memory and
batch rows as flags, but always uses the default batch byte target and
presents types by `UdfType::default_sql_type`. `FUNCTION` arguments name a
guest function, or give its full signature when the name is overloaded. A
flat list is presented as an array and nested lists as SQL lists, and
`timestamp` is never presented as `timestamptz`.

Local, no connection needed:

- `mz udf check <module>`: validates the module and ABI version, prints its
  size and hash, lists every exported signature with the SQL signature it
  maps to (or why it cannot map), and warns about `random_get`,
  `clock_time_get` and `poll_oneoff`.
- `mz udf check <module> --determinism <function>`: checks the batching
  contract ([Batch semantics](#batch-semantics)) on 16,384 rows generated
  from the argument types, or on a headerless CSV file with `--input
  cases.csv`. It runs the rows in one batch (of `--batch-rows` if given),
  one row per call, in batches of seven, and in reverse order, reports the
  rows whose outcome differs, and fails on empty input or if no row the
  guest was called on succeeds. `--rows` and `--seed` change the generated
  rows.
- `mz udf sql <module> <function> [--name n] [--module-name m] [--strict]
  [--fuel f] [--memory m]`: prints a ready-to-run psql script that creates
  the module, with the base64 passed to `\bind`, and the function. It skips
  the determinism check.
- `mz udf call <module> <function> [--] <args...>`: invokes the function
  with arguments in PostgreSQL text format, as `COPY` reads them, or `NULL`.
  Arguments starting with a hyphen, such as negative numbers, follow `--`.
  It prints the result or error, and on stderr the number of guest calls and
  bisections, fuel used, peak linear memory and captured output. Trap errors
  include the guest's panic message and a backtrace with name-section names.
- `mz udf call ... --input cases.csv`: the same for every row of a
  headerless CSV file, run through the batched path.

Every subcommand that calls or declares a function takes `--fuel` and
`--memory` to override the defaults, and `--strict` to return `NULL` without
a call for a row with a `NULL` argument, as a `STRICT` function does in a
region. Those that call a function locally also take `--batch-rows`. `sql`
and `create` declare the fuel, memory and strictness they are given.

Against a region, each command taking `--database` to choose the database:

- `mz udf create <module> <function> [--name n] [--module-name m] [--schema
  s] [--database d] [--strict] [--fuel f] [--memory m] [--skip-check]`: runs
  the determinism check on generated rows with those limits, then creates the
  function. It reuses a module of that name whose hash matches, which needs
  only `USAGE` on it, creates the module if there is none (which needs psql
  16 or later, for `\bind`), and refuses if one exists with other bytes. The
  function binds the module by catalog id, so a module dropped and recreated
  under the same name between the hash check and the binding fails the
  statement instead of taking the checked module's place. If creating the
  function fails after creating the module, the module stays, and `create`
  says so. `--skip-check` skips the determinism check.
- `mz udf pull <function> [-o out.wasm]`, or `mz udf pull --module <module>`:
  finds the function's module and downloads it (from `SHOW CREATE WASM
  MODULE`), and prints its hash, to confirm what is actually running. Names
  are SQL syntax, so a name `create` was given with uppercase letters or
  special characters is quoted here. It writes the module even if this
  version of `mz` would no longer accept it, and warns.
- `mz udf replay <module> <function> --query 'SELECT a, b FROM t WHERE ...'`:
  runs a query in the region, feeds the result rows through the local
  runtime, and reports the rows that error, with their arguments. This is the
  answer to "my MV has a `gcd: trap` error, which input caused it?". Cluster
  errors deliberately omit argument values, which may be large or sensitive.

`mz` has no in-process Postgres client: it shells out to `psql`. The region
commands do too, with `-X` so that no startup file changes the output,
sending SQL on stdin, because an 8 MB module does not fit in a command-line
argument. The database goes into the connection URL as an encoded `dbname`
parameter, so any name arrives intact. Names and queries from the command
line are parsed before they go into that script, so they cannot carry
further statements or psql commands. `replay` reads its query's results in
`COPY ... TO STDOUT` text format, which `mz_pgcopy` decodes into typed rows,
and `pull` and `create` read query output with a zero byte between fields,
which no name can contain. Depending on psql costs the commands a version
requirement and a separate session per step, which is why `create` binds by
id rather than relying on the steps running together. `mz` is also
Cloud-only, since every connection goes through a Frontegg app password and
the Cloud region API. The local commands work anywhere.

`mz-deploy` already has a `tokio-postgres` client, host/port profiles and a
Docker sandbox. Whether the region commands belong there as well is an open
question. Profiling with wasmtime's `GuestProfiler`, which writes Firefox
Profiler files that show where fuel goes, is future work.

### Where the code goes

- `src/wasm-udf-abi` (`mz-wasm-udf-abi`): the guest contract without a
  runtime. Signature strings and their export-name encoding, the SQL to
  arrow-udf type mapping, the WASI preview1 function list, default limits,
  and `ModuleInfo::parse`, which validates a module with `wasmparser` alone.
  `mz_sql` uses it for `CREATE WASM MODULE` and `CREATE FUNCTION`, so
  the environmentd binary does not link wasmtime. The combined
  `materialized` binary does, through clusterd, but its environmentd
  process never installs a runtime.
- `src/wasm-udf` (`mz-wasm-udf`): the engine configuration, the
  deterministic WASI implementation, the Arrow IPC codec, single calls in
  fresh instances, the `WasmInvoker` implementation with bisection and batch
  sizing, and the process-wide module cache. It depends on `wasmtime`
  (Cranelift, on-demand allocator), `wasmparser` and `arrow` (already a
  workspace dependency; the IPC format is stable, so the host's arrow version
  is independent of the guest's). The license check (`deny.toml`,
  `about.toml`) needs Apache-2.0 WITH LLVM-exception, which the Bytecode
  Alliance crates use and which is already allowed. A guest fixture crate and
  its gzipped build live under `src/wasm-udf/tests/fixtures`.
- `src/expr`: `VariadicFunc::Wasm`, the `WasmInvoker` and `WasmRuntime`
  traits, `EvalError::WasmFunction`, the batched MFP evaluator, and the
  constant-folding guard.
- `src/compute`, `src/compute-client`, `src/compute-types`: the
  `InstallWasmModule` and `DropWasmModule` commands, installing modules only
  where dataflows and peeks reference them, the batched render paths, and

- `src/sql-parser`, `src/sql`: grammar, planning, the feature flag, the
  `CREATEWASMMODULE` system privilege and limits.
- `src/catalog`, `src/adapter`: the module and function catalog items, the
  catalog version bump, builtin rows and views, and module registration with
  the compute controller.
- `src/mz`: `mz udf`.
- `src/environmentd/tests/wasm_udf.rs`: end-to-end tests over SQL, including
  a restart.

## Minimal Viable Prototype

The implementation is behind `enable_wasm_functions`, with a fixture guest
crate (`src/wasm-udf/tests/fixtures/udfs`) exercising every behavior the
runtime guarantees: per-row guest errors, traps, fuel and memory limits
attributed to rows by bisection, the deterministic WASI stubs, captured
output, a stateful guest that breaks the per-row contract, and a `batch_fn`
guest that receives ten thousand rows in one call. Planning, batched MFP
evaluation, and an end-to-end test over SQL (including a restart) cover the
rest.

The measurements still to take, which set the default batch size and limits:

1. A criterion benchmark of amortized per-row cost for `gcd`, a string
   function, and `saxpy` at batch sizes 1, 16, 128, 1024 and 16K, broken
   down into instantiation, IPC encode and decode, and guest time.
2. Fuel overhead (on versus off), fuel calibrated against wall time, and the
   cost of bisection for a function that traps on 1% of rows.
3. An MV over 10M rows with a UDF against the same MV with a builtin, and
   against the per-row fallback.

They also decide whether IPC file format is good enough or whether we
propose a faster transport upstream.

## Alternatives

**Component model with WIT types, row-at-a-time.** The first draft of this
design. Each SQL function is a typed WIT export, invoked once per row with
canonical-ABI lowering. It has self-describing signatures, and existing
tooling generates bindings for Rust, Go, C, Python and JS. We rejected it for
three reasons:

- It requires designing and maintaining a third SQL type mapping, in WIT,
  including every composite type, next to the Arrow mapping we already
  maintain.
- Row-at-a-time calls pay instantiation and call overhead per row, and
  keeping it low needs either instance reuse (a determinism risk) or
  micro-optimizing a path that batching amortizes anyway.
- It is incompatible with the RisingWave and Databend guest ecosystem.

The component model remains a candidate for a second ABI if Python or JS
guests become a priority. It could carry Arrow IPC through a typed transport
(`eval: func(batch: list<u8>) -> result<list<u8>, string>`), which would keep
the Arrow type boundary and the batched evaluator unchanged.

**One instance per row.** Calling the guest once per row, each time in a
fresh instance, would make the batching contract hold by construction. On
the test fixture (optimized build, macOS, one thread) it costs 31 to 36 µs
per row, against 50 ns (`gcd`) to 430 ns (`jaro_winkler`) per row in batches
of 16K, so 75 to 650 times slower. Instantiation is only part of it: 18.6 µs,
or 12.2 µs with wasmtime's pooling allocator. The rest is fixed work on every
arrow-udf call, about 176K fuel in the guest to read and write the IPC files
and about 4 µs of host encoding. A cheaper reset would not remove that
floor, and restoring a memory snapshot instead is not possible because the
guest's mutable globals are not exported. It remains a candidate as a
per-function opt-in for expensive functions.

**Core module with a custom scalar ABI** (ScyllaDB style: fixed-width values
as Wasm scalars, variable-length ones as pointer and length). This has the
lowest per-call overhead but no batching, no ecosystem, and signatures that
are not self-describing. Rejected.

**arrow-udf-runtime as the host.** It would save host code, but it
configures no fuel, epoch or memory limit, reuses instances from a pool, uses
the legacy `wasi-common` crate with a real clock and random source, and has
no notion of per-row semantics under batching. The host is where Materialize's
guarantees live, so we write our own and share only the guest ABI.

**Evaluating UDFs in environmentd (allowing constant folding).** This would
put a Wasm runtime and untrusted code execution on the coordinator, and make
DDL and query planning latency depend on user code. Not folding costs little:
constant UDF calls are rare, and when they occur they run on a cluster like
any other query.

**Waiting for columnar scalar evaluation.** Evaluating all scalar expressions
over columns would make UDF batching fall out naturally, and would help
builtins too. Only its first step exists: plans of `Int64` arithmetic and
comparisons run a column at a time. Covering every function is a much larger
project, and UDFs are not viable without batching, so this design batches at
UDF call sites. It is built to be absorbed by that work rather than to
compete with it ([Columnar scalar evaluation](#columnar-scalar-evaluation)).

## Open Questions

1. **Batch size and limits.** Are 16K rows, 8 MB, 100M fuel and 64 MiB the
   right defaults? Benchmarks decide this.
2. **Calls in lazy positions.** Precompute-and-replay runs a call under
   `If` on every live row, including rows that take the other branch. For an
   expensive function behind a selective condition, partitioning rows on the
   condition first would send the guest fewer rows. Is that worth the extra
   evaluator machinery, or does it wait for a columnar evaluator that
   carries selection masks through branches?
3. **CLI home.** `mz udf` lives in `mz`, as asked. `mz-deploy` has a
   `tokio-postgres` client, host/port profiles for self-managed regions, and
   a Docker sandbox in which a test command could run a real Materialize.
   Should project integration (functions as `.wasm` artifacts in an
   `mz-deploy` project) live there?
4. **ABI evolution.** arrow-udf is 0.x, and its last major ABI revision
   renamed the signature types we bind on. Persisted modules must keep
   running whatever upstream does, so we own the 3.0 profile we accept from
   now on. If IPC file overhead shows up in profiles, a faster transport
   (IPC stream format, or C Data Interface input) has to be an optional
   capability that leaves the 3.0 entry points in place, or a new major
   version, not a mandatory 3.1. Do we pursue that upstream, or ship a thin
   `mz-udf` guest crate that pins and re-exports the arrow-udf macros?
5. **Seeded randomness.** Is a deterministic `random_get` the right default,
   or should modules that import it be rejected unless the user opts in?
   Rejecting would break most Rust modules that use `HashMap`.
6. **Privileges.** Do we add a per-function `EXECUTE` privilege now, or later
   alongside other RBAC work? Postgres grants `EXECUTE` to `PUBLIC` by
   default, so adding it later is compatible. Until then, an administrator
   cannot revoke access to one function while keeping the rest of its
   schema, and `USAGE` on a schema also lets a role read the modules in it
   through `SHOW CREATE WASM MODULE`.
7. **Overloads.** Catalog items are unique by name within a schema. Supporting
   overloaded user functions would mean making the name plus argument types
   the item's identity, which touches name resolution broadly. It would also
   be the time to resolve functions across schemas the way Postgres does
   ([Catalog and planning](#catalog-and-planning)), which changes which
   function some existing queries resolve to.
8. **Checking the contract in the region.** Only `mz udf create` checks the
   batching contract. Running the same check when `CREATE FUNCTION` is
   sequenced would cover every client, but environmentd does not run guest
   code, so the coordinator would have to ask a replica of the session's
   cluster to run it. A complementary runtime check could rerun a sample of
   rows alone and, on a mismatch, stall the dataflow instead of writing data.
   Are either worth their machinery?
9. **Sandbox review.** Guest code runs inside clusterd, which holds persist
   and cloud credentials. wasmtime's isolation has a strong record, but this
   needs a security review, including Spectre mitigations and a policy for
   wasmtime upgrades.

### Columnar scalar evaluation

The longer-term direction for scalar execution is to evaluate MFPs over
columns: each input column is a typed vector with per-row null and error
markers, each function runs once per batch over whole columns, and the
evaluator tracks which rows are still live. UDF batching becomes one case of
that, and most of what this design adds to the evaluator goes away.

The two agree on semantics. A columnar evaluator must produce exactly the
rows and errors that row-at-a-time evaluation would, charging an error to a
row only if per-row evaluation would have reached that expression. That is
the same guarantee precompute-and-replay gives, so a plan can move from one
evaluator to the other without changing its results.

How the pieces fit:

- **A UDF call is a function with a batch form.** `VariadicFunc::Wasm`
  converts its argument columns to Arrow, makes one guest call through the
  `WasmInvoker` trait, and returns a result column. Typed vectors map to
  Arrow arrays with little or no per-row work, which is cheaper than building
  Arrow arrays from `Datum`s as this design does. The runtime, its batch
  semantics, bisection and resource limits are unchanged, since they sit
  behind the trait.
- **Batch evaluation takes a selection of live rows.** Builtin kernels may
  ignore it, because computing a cheap function on dead rows and discarding
  the result costs little. The UDF batch form must honor it, gathering only
  live rows for the guest, for the reason given in
  [The batched evaluator](#the-batched-evaluator).
- **Lazy constructs batch under selections.** `If`, `COALESCE`, `AND` and
  `OR` evaluate each branch only on the rows the condition sends to it. That
  removes the cost noted in
  [Open questions](#open-questions): a call in a lazy position no longer
  runs on rows that take the other branch.
- **Unbatchable subexpressions fall back per subexpression.** A function
  without a batch form is evaluated row by row into a column, and evaluation
  continues in columns, so one such function does not send a whole plan back
  to row-at-a-time. The first column path does not do this yet: a plan with
  any node outside its kernels runs on the row loop. Evaluating such plans a
  column at a time with per-row fallbacks measured slower than the row loop,
  by 18% on a text predicate, so the fallback has to cost no more than the
  row loop before it replaces it.

Once lazy constructs batch and fallback is per subexpression, every plan
that calls a UDF is batchable, and the replay frame and the evaluator in
`mz_expr::linear::wasm` are removed. Both sites already call
`evaluate_batch` with rows it reads by index, and the column path behind it
extracts only the columns it reads, so a broader columnar evaluator needs no
change at the sites.
`persist_source` can then fill batches from a part's columns instead of from
decoded rows, with filter pushdown unchanged.

Join closures, `Reduce` key and value plans, and peeks are per-row call sites
for any evaluator, columnar or not, and need the operator changes listed
above.
