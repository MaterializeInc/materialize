# WebAssembly user-defined functions

- Associated: (none yet)

## The Problem

Materialize has no user-defined functions. Users who need logic outside the
builtin function set (domain-specific parsing, scoring, hashing, geo math,
custom encodings) have to precompute it upstream, before the data reaches a
source, or write it as long SQL expressions that are hard to test and slow to
plan. Other streaming databases (RisingWave, Databend, SingleStore, ScyllaDB)
let users ship compiled functions as WebAssembly modules and call them from
SQL.

We want the same, with the RisingWave SQL surface and guest ABI:

```sql
\set wasm_binary `base64 -i path/to/udf.wasm`
CREATE FUNCTION gcd(int, int) RETURNS int LANGUAGE wasm USING BASE64 :'wasm_binary';
SELECT gcd(a, b) FROM t;
```

Two constraints make this harder for Materialize than for a batch database:

1. **Functions must be deterministic.** Differential dataflow retracts a row
   by recomputing it. If `f(x)` returns a different value at retraction time
   than at insertion time, the retraction does not cancel the insertion. This
   leaves negative multiplicities in arrangements, and a single impure UDF can
   make a replica produce wrong answers or crash. Replicas of one cluster must
   also agree with each other. A batch database can trust an `IMMUTABLE`
   label that the user gets wrong. We cannot.
2. **Expression evaluation is row-at-a-time.** `SafeMfpPlan::evaluate_inner`
   evaluates one row's datums at a time, inside a timely worker that must not
   block. Crossing into Wasm has a fixed cost per call (instantiation,
   encoding, the call itself), so UDFs are only viable if that cost is spread
   over many rows. Batching is a requirement, not an optimization we add
   later.

## Success Criteria

- A user can build a function in Rust with the `arrow-udf` crate's
  `#[function]` macro, register it with `CREATE FUNCTION ... LANGUAGE wasm
  USING BASE64 '...'`, and use it in `SELECT`, views, indexes, materialized
  views and subscribes. A module built for RisingWave loads unchanged.
- The same module, arguments and Materialize version always produce the same
  result or the same error. This holds across replicas, across restarts,
  between insertion and retraction, and regardless of how rows were grouped
  into batches.
- A misbehaving module (infinite loop, runaway allocation, trap) produces a
  SQL error for the offending row. It never stalls a worker indefinitely,
  exhausts replica memory, or crashes clusterd.
- A user can reproduce and debug a failing call locally with the `mz` CLI,
  using the same runtime configuration, type mapping, batching and limits as
  the cluster.
- Amortized per-row overhead for a trivial function (`gcd(int, int)`) at full
  batch size is measured and published. The target is under 100 ns per row.
  arrow-udf's own benchmark (15.5 µs per 1024 rows) suggests this is
  achievable.
- Plans without UDFs are not slowed down.

## Out of Scope

- Aggregate functions and table functions. arrow-udf defines a table-function
  ABI (`->>` signatures, `record_batch_iterator_next`), which we can adopt
  later ([Future work](#future-work)).
- Non-deterministic functions, in particular any real access to clocks,
  randomness, the network, the filesystem or environment variables.
- Inline source compilation (RisingWave's `LANGUAGE rust AS $$ ... $$`). That
  requires a compiler toolchain in environmentd, which we do not want.
- Remote or external UDFs (HTTP, Arrow Flight). They cannot be made
  deterministic.
- Loading modules from a URL, S3 or a file path (`USING LINK`). v1 accepts
  only an inline literal.
- Guest languages other than Rust. The ABI works for any language that can
  produce a wasm32 core module and link an Arrow IPC implementation, but only
  Rust has a maintained SDK today.
- Overloads: two user functions with the same name and different argument
  types in one schema.
- UDFs in expressions evaluated outside compute clusters: Kafka sink
  `PARTITION BY`, column `DEFAULT`s, and anything else environmentd or
  storage evaluates. These are rejected at plan time.

## Solution Proposal

In summary:

- **ABI.** Guests implement the `arrow-udf` 3.0 ABI: a wasm32-wasip1 core
  module that exports one function per signature. Each call receives an Arrow
  IPC record batch and returns one. We write our own host rather than using
  `arrow-udf-runtime`, because the host is where determinism and resource
  limits are enforced, and that runtime configures neither.
- **Batching.** A new batched MFP evaluator groups the rows that reach a UDF
  call site, makes one guest call per batch, and resumes per-row evaluation
  with the results. Per-row evaluation order, predicate short-circuiting and
  error semantics are unchanged.
- **Semantics are per row.** The result for a row is defined as the result of
  calling the function on a batch containing only that row, in a fresh
  instance, under the configured limits. Larger batches are an optimization.
  A batch-level failure is resolved by bisecting the batch until every row
  has its own deterministic outcome.
- **Runtime.** A new crate, `mz-wasm-udf`, owns the wasmtime engine
  configuration, the SQL-to-Arrow type mapping, the batch call path and the
  resource limits. clusterd and the `mz` CLI both link it. `mz_expr` depends
  only on a small trait that the crate implements, so neither environmentd
  nor anything else that links `mz_expr` pulls in wasmtime.
- **Catalog and planning.** `CREATE FUNCTION` creates a user `Func` catalog
  item that stores its `create_sql` like other user items. The planner
  resolves calls to a new `VariadicFunc::Wasm` variant, which carries a module
  hash rather than the module bytes. Calls are never constant-folded, so
  environmentd validates modules but never runs them.
- **Distribution.** Compute commands that carry scalar expressions also carry
  the bytes of the modules they reference, keyed by hash. Clusterd compiles
  each module once per process.
- **Devex.** `mz udf` subcommands scaffold, check, call, profile, replay and
  upload modules.

### SQL surface

```sql
CREATE FUNCTION [IF NOT EXISTS] name ( [argname] argtype [, ...] )
    RETURNS rettype
    LANGUAGE wasm
    [IMMUTABLE]
    [STRICT | RETURNS NULL ON NULL INPUT | CALLED ON NULL INPUT]
    USING BASE64 'base64 text'
    [WITH ( EXPORT = 'export-name', FUEL = <int>, MEMORY = '<size>' )];

DROP FUNCTION [IF EXISTS] name [CASCADE | RESTRICT];
```

- `USING BASE64` follows RisingWave. Whitespace in the literal is ignored, so
  psql's `\set wasm_binary \`base64 -i f.wasm\`` works whether or not `base64`
  wraps lines (macOS `base64 -i`, Linux `base64 -w0`).
- `EXPORT` names the guest function to bind, which defaults to the SQL
  function's name. The host rebuilds the arrow-udf signature string from
  `EXPORT` and the SQL signature, then looks up the matching export. So one
  module can back several SQL functions, and a SQL name can differ from the
  name used in the guest's `#[function]` attribute.
- `FUEL` and `MEMORY` override the per-call limits, up to ceilings set by
  system variables ([Resource limits](#resource-limits)).
- `IMMUTABLE` is accepted and is the only volatility allowed. `STABLE` and
  `VOLATILE` are rejected with an error explaining the determinism
  requirement.
- Null handling defaults to `CALLED ON NULL INPUT`, as in Postgres
  ([Nulls](#nulls)).
- `CREATE OR REPLACE FUNCTION` and `ALTER FUNCTION` are not supported. Running
  dataflows are compiled against a specific module, and swapping it
  underneath them would break determinism. Users replace a function by
  creating a new one and migrating dependents, as with views. Blue/green
  deployments via `mz-deploy` already work this way.

All of this is behind a feature flag, `enable_wasm_functions`, declared with
`enable_for_item_parsing: true` so existing functions still load at boot
after the flag is turned off. Per repo policy it defaults off in production
and on in CI via `system_parameter_default`.

Privileges follow Postgres defaults for v1. Creating a function needs `CREATE`
on the schema. Calling one needs `USAGE` on the schema. There is no
per-function `EXECUTE` privilege yet ([Open questions](#open-questions)).

### Guest ABI: arrow-udf 3.0

We adopt the ABI that the [`arrow-udf`](https://github.com/arrow-udf/arrow-udf)
guest crate produces, unchanged. A module is a wasm32-wasip1 core module with
these exports:

| Export | Signature | Purpose |
|---|---|---|
| `ARROWUDF_VERSION_3_<minor>` | static, name only | ABI version. The host accepts major version 3. |
| `alloc` | `(len: usize, align: usize) -> *mut u8` | Guest allocator. |
| `dealloc` | `(ptr, len, align)` | |
| `arrowudf_<b64(sig)>` | `(ptr, len, out: *mut CSlice) -> i32` | One per scalar function. |
| `memory` | | Linear memory. |

`sig` is `name(t1,t2,...)->ret`, encoded as unpadded base64 over the alphabet
`A-Za-z0-9$_` so that it is a valid symbol. `usize` is `i32` on wasm32, and
`CSlice` is `{ ptr: i32, len: i32 }`.

A call works as follows:

1. The host allocates `len + 8` bytes with `alloc(len + 8, 4)` and writes an
   Arrow IPC *file* containing one record batch at offset 8. The batch has
   one column per argument.
2. The host calls `arrowudf_<sig>(ptr + 8, len, ptr)`. The first 8 bytes of
   the allocation receive the output `CSlice`.
3. A return value of `0` means the slice holds an IPC file with one record
   batch. Column 0 is the result, with one row per input row. An optional
   second column named `error`, of type `Utf8`, holds per-row error messages.
4. A return value of `-1` means the slice holds a UTF-8 error message for the
   whole call.
5. The host copies the output and frees both buffers with `dealloc`.

The guest macro generates the per-row loop, so the ABI itself is
batch-shaped. RisingWave's host always sends one input chunk per call. Ours
sends one batch per UDF call site per group of rows
([Batched evaluation](#batched-evaluation)).

Adopting the ABI as-is means RisingWave and Databend modules, the
`#[function("gcd(int, int) -> int")]` macro and its documentation all work
for Materialize. The host is ours, so everything Materialize-specific is
enforced there, not in the guest: determinism, limits, bisection and type
validation.

The ABI has known warts that we either accept or work around:

- Table-function iterators drop errors. This does not affect v1, which is
  scalar only.
- The input is IPC *file* format, which adds a footer and schema per call.
  At 1024 rows this is a small fraction of the cost. A future
  `ARROWUDF_VERSION_3_1` extension could accept IPC stream format, or
  C Data Interface buffers written directly into guest memory, if profiling
  justifies it. That would be a proposal to upstream, not a fork.
- The signature lives in the export name, not in a typed schema. This is
  enough to validate modules at DDL time, since environmentd only has to
  parse export names ([Planning](#catalog-and-planning)).

#### Type mapping

The SQL signature determines the arrow-udf type name used for export lookup
and the Arrow `DataType` used for encoding. The codec (`mz_wasm_udf::codec`)
is separate from `mz_arrow_util`'s COPY TO and Iceberg mapping, because the
representations differ for most non-trivial types: arrow-udf guests expect
`Utf8`, `Binary`, and decimal text where `mz_arrow_util` chooses `LargeUtf8`,
`LargeBinary`, and `Decimal128`, and reading values back needs validation
that file readers do not.

| SQL type | arrow-udf type | Arrow encoding |
|---|---|---|
| `boolean` | `boolean` | `Boolean` |
| `smallint`, `integer`, `bigint` | `int16`, `int32`, `int64` | `Int16`, `Int32`, `Int64` |
| `uint2`, `uint4`, `uint8` | `uint16`, `uint32`, `uint64` | `UInt16`, `UInt32`, `UInt64` |
| `real`, `double precision` | `float32`, `float64` | `Float32`, `Float64` |
| `numeric` | `decimal` | `Utf8`, extension `arrowudf.decimal` |
| `date` | `date32` | `Date32` |
| `time` | `time64` | `Time64(Microsecond)` |
| `timestamp`, `timestamptz` | `timestamp` | `Timestamp(Microsecond, None)`, UTC for `timestamptz` |
| `interval` | `interval` | `Interval(MonthDayNano)` |
| `jsonb` | `json` | `Utf8`, extension `arrowudf.json` |
| `text`, `varchar`, `char` | `string` | `Utf8` |
| `bytea` | `binary` | `Binary` |
| `T list`, one-dimensional `T[]` | `T[]` | `List` |

Notes:

- Numeric crosses as decimal text, which is lossless, unlike a fixed
  `Decimal128(38, s)`.
- Intervals cross as nanoseconds. Materialize stores microseconds as `i64`, so
  intervals longer than about 292 years overflow on the way in, which is an
  evaluation error for that row. Sub-microsecond parts of returned intervals
  are truncated toward zero.
- Records (arrow-udf `struct` types, declared by `arrowudt_` exports), `uuid`,
  maps, ranges, multi-dimensional arrays, and types without an arrow-udf name
  are rejected at `CREATE FUNCTION`.
- Return types cannot carry type modifiers (`varchar(n)`, `numeric(p, s)`,
  `timestamp(p)`), so a returned value never has to be checked against one.
- Values coming back from the guest are validated: `decimal` and `json` text
  must parse, and dates, times, and timestamps must be in range. A failure is
  an evaluation error for that row, not a panic.

#### Nulls

The arrow-udf macro decides strictness inside the guest: a non-`Option`
parameter makes the generated loop emit `NULL` without calling the user's
code. The host cannot see this from the export name, so it cannot infer
optimizer properties from the binary. Instead:

- `STRICT` (or `RETURNS NULL ON NULL INPUT`) tells both the host and the
  optimizer. The host removes rows with a `NULL` argument from the batch and
  returns `NULL` for them without calling the guest. `propagates_nulls` is
  true.
- `CALLED ON NULL INPUT`, the default, passes `NULL`s to the guest.
  `propagates_nulls` is false.
- `introduces_nulls` is always true, since the guest can return `NULL` for
  any row.

A mismatch between the declaration and the guest is harmless. A `STRICT`
declaration on a guest taking `Option` means the guest never sees `NULL`s,
which is what the declaration says. A `CALLED ON NULL INPUT` declaration on a
strict guest only costs the optimizer information.

#### Errors

A row's call can fail in five ways, and each becomes an
`EvalError::WasmFunction { name, kind, message }` for that row:

- The guest returns a message in the `error` column (the function's `Result`
  was `Err`).
- The call traps: a panic (which aborts under `wasm32-wasip1`),
  `unreachable`, or an out-of-bounds access.
- The call runs out of fuel.
- The call hits the memory limit.
- The guest returns `-1` for the whole call.

The last four are batch-level failures. They are attributed to rows by
bisection ([Batch semantics](#batch-semantics)).

Errors flow into persist, so their text must be deterministic. Messages carry
the function's qualified name, the kind, and the guest message or the trap
description with a Wasm backtrace. The backtrace uses function names from the
module's name section and Wasm code offsets, which are properties of the
binary. Messages never include host addresses or timings. The new
`EvalError` variant needs a matching `ProtoEvalError` addition, which is
backward compatible.

#### Imports

arrow-udf modules are `wasm32-wasip1` binaries, so they import
`wasi_snapshot_preview1`. Rust std reaches some of these imports even in pure
code: the default `HashMap` hasher seeds itself from `random_get`. So the host
provides a complete, deterministic preview1 implementation instead of trapping
on use. The implementation is our own (`mz_wasm_udf`'s `wasi` module), about
50 small host functions, rather than `wasmtime-wasi`: that crate's preview1
support pulls in the component model, async runtimes, and capability-based
filesystem access, and every behavior here is a fixed answer that is easier
to audit for determinism when written out:

| Capability | Behavior |
|---|---|
| `random_get` | Deterministic SplitMix64 stream with a fixed seed, reset per instance. |
| `clock_time_get`, `clock_res_get` | Frozen at the Unix epoch. |
| `poll_oneoff` (sleep) | Returns immediately, reporting every clock subscription as elapsed. |
| `environ_*`, `args_*` | Empty. |
| Filesystem | No preopens, so every file and path operation fails with `EBADF`. |
| `fd_write` on stdout and stderr | Captured, capped at 4 KiB per call ([Logging](#logging)). |
| `proc_exit` | Trap with the exit code. |
| Sockets | Linked, and fail with `ENOTSUP`. |

The ABI crate lists every preview1 function with its signature, and a test
checks that the runtime's linker defines exactly that list, so validation in
environmentd and linking in clusterd cannot drift apart.

Seeding `random_get` means `HashMap` iteration order inside the guest is
fixed. That is what we want, but it is also a sharp edge for anyone who calls
`rand` expecting randomness. The docs must say so, and `mz udf check` warns
about modules that import `random_get` or `clock_time_get`. Any import
outside `wasi_snapshot_preview1` fails `CREATE FUNCTION`.

### Batched evaluation

#### Call sites

A UDF call is *batchable* when it sits in a *strict* position of an MFP
expression or predicate: one that is evaluated whenever its enclosing
expression is, and whose error always becomes the enclosing expression's
error (`OptimizableExpr::strict_children_mut`). Arguments of ordinary
functions are strict. Branches of `If`, everything after the first input of
`COALESCE` and case lookups, and every input of `AND` and `OR` (which absorb
errors when another input is false or true) are not.

When the batched plan is built, each batchable call is lifted out of its
expression into a batched step of its own, innermost calls first, and
replaced by a reference to the step's column. Lifting can change which of
several errors a row reports, but never whether it reports one, which is the
latitude MFP memoization already takes.

Calls in other positions stay where they are and are evaluated through the
per-row path as batches of one. That is correct but slow.

#### The batched evaluator

`BatchedSafeMfpPlan` (`mz_expr::linear::batch`) is the batched counterpart to
`SafeMfpPlan::evaluate_inner`. It takes a batch of input rows, holds a datum
vector per row in one arena that lives for the batch, and runs the MFP in
stages separated by batched calls:

1. For each live row, run the expressions and predicates up to the next call
   site, in the order `evaluate_inner` uses. A row whose predicate fails is
   dropped, and a row that errors is finalized with its error.
2. Collect the call's arguments from the remaining live rows and make one
   batch call through the `WasmInvoker` trait. It returns one `Result<Datum,
   EvalError>` per row, allocated in the batch arena.
3. Push each row's result onto its datum vector, or finalize the row with its
   error, and continue with the next stage.
4. Project the surviving rows.

Because each row goes through the same expressions and predicates in the
same order as `evaluate_inner`, the result for every row is identical to the
per-row evaluator's. A predicate placed before a UDF still stops the UDF from
seeing rows that fail it, which the optimizer already arranges for pushed-down
filters.

When an MFP has no batchable call, render sites keep the existing per-row
closure, so plans without UDFs pay nothing.

#### Batch sizes and vectorized guests

The ABI is batch-shaped, and so is the guest side of it. One guest call
carries a whole Arrow batch, and the guest decides how to process it:

- The `#[function]` macro's generated export loops over rows inside the
  guest, so even a scalar Rust function crosses the boundary once per batch.
- For functions whose arguments and result are primitive numbers, the macro
  generates SIMD kernels over whole arrays.
- `#[function("...", batch_fn = "f")]` hands `f` the input columns as Arrow
  arrays and takes its output column back, so the guest can use Arrow compute
  kernels or any other vectorized code. The fixture's `saxpy` is an example.

For this to pay off, batches must be large. Render sites accumulate every
container that arrives in one operator activation into a single batch
(`flat_map_rows_batched`), and the invoker splits it only at
`wasm_udf_batch_max_rows` rows (default 16K) and `wasm_udf_batch_max_bytes`
of encoded input (default 8 MiB), both replica-scoped dyncfgs. A test checks
that ten thousand rows reach a `batch_fn` guest in one call.

#### Where MFPs are evaluated

| Site | Batching |
|---|---|
| `Mfp` render over collections and arrangements (`render/context.rs`) | Batched over each activation's input. MFPs that seek to a literal key value stay on the fused per-row arrangement path. |
| Source imports (`persist_source`) | The MFP is kept out of the source and applied batched to the source's output. This gives up persist filter pushdown for that MFP. |
| `Reduce` key and value plans | Per row. |
| MFP after a table function | Per row. |
| Peek result iteration | Per row. |
| Join closures | Per row. |

The per-row sites are correct, and become batched as follow-up work
([Future work](#future-work)). `MfpPlan`'s temporal bounds (`mz_now()`
filters) are evaluated per row after the batched stages.

#### The `WasmInvoker` boundary

`mz_expr` must not depend on wasmtime. Everything that links `mz_expr`,
environmentd included, would otherwise pull in Cranelift. `WasmFunc`
therefore carries a handle to an object implementing a trait defined in
`mz_expr`:

```rust
pub trait WasmInvoker: Send + Sync + Debug {
    /// Calls the function on each row of `args` and returns one result per
    /// row, in order. The outcome for a row does not depend on the other
    /// rows in the batch.
    fn call_batch<'a>(
        &self,
        args: &[&[Datum<'a>]],
        arena: &'a RowArena,
        out: &mut Vec<Result<Datum<'a>, EvalError>>,
    );
}
```

`mz-wasm-udf` implements it. A process that evaluates UDFs installs a
process-wide `WasmRuntime` (`mz_expr::func::install_wasm_runtime`), and each
`WasmFunc` binds itself to an invoker from it on first use, caching the
binding in a cell that is not part of its identity. The scalar `eval` path,
which is the per-row fallback, calls `call_batch` with one row. Evaluating a
`WasmFunc` without a runtime, or whose module is not installed, returns
`EvalError::Internal`, which can only happen through a bug, since
environmentd never evaluates UDF calls.

### Batch semantics

The contract that keeps batching deterministic is:

> The outcome for a row (value or error) is the outcome of calling the
> function on a batch containing only that row, in a fresh instance, with the
> function's fuel and memory limits.

The host makes every observed outcome match that definition:

- **Fresh instance per batch.** Each batch runs in a newly instantiated
  module, created from a pre-linked `InstancePre` with copy-on-write memory
  images. No state survives between batches.
- **Per-row errors are final.** An entry in the `error` column is the guest's
  answer for that row.
- **Batch-level failures bisect.** If a batch traps, runs out of fuel, hits
  the memory limit or returns `-1`, the host splits it in half and retries
  each half in a fresh instance, down to single rows. A single-row failure is
  that row's error. Rows in halves that succeed get their values.
- **One limit for all batch sizes.** Fuel and memory limits apply to every
  call, whatever its size. A batch that completes within the limits proves
  that each of its rows would complete alone, provided the cost of a row
  alone is no greater than the cost of any batch containing it. That holds
  whenever rows do not affect each other's work, and also for per-instance
  caches, because the batch pays for warming the cache itself. So a cheap
  function runs at full batch size, and a heavy one converges to batches of
  about `limit / cost_per_row` rows. The host keeps a per-function estimate
  of fuel per row and sizes the next batch from it. Batch sizing never
  changes results, so the estimate does not need to be deterministic.

What the host cannot verify is that output row `i` depends only on input row
`i`. A guest can deliberately compute something across the batch (a running
counter, batch statistics). That breaks determinism, and no host-side
mechanism detects it cheaply. It is part of the documented contract, and
`mz udf check --determinism` tests for it
([Developer experience](#developer-experience)).

Bisection costs up to `2 log2(N)` extra calls, spent only on rows that fail
or on functions near their limits. A function that errors on a large fraction
of rows through traps rather than through its `error` column runs much
slower than one that returns `Err`. The docs should recommend returning
`Result`.

### Determinism

Wasm is deterministic apart from a short list of documented exceptions. The
engine configuration closes each one, and `mz-wasm-udf` owns that
configuration as a single constant shared by clusterd and the CLI.

| Source of nondeterminism | Mitigation |
|---|---|
| NaN bit patterns | `cranelift_nan_canonicalization(true)` |
| Relaxed SIMD | `wasm_relaxed_simd(false)` |
| Threads, shared memory | `wasm_threads(false)` |
| Host capabilities | Deterministic preview1 context ([Imports](#imports)) |
| Wall-clock timeouts | Fuel only, no epoch interruption ([Resource limits](#resource-limits)) |
| State carried between calls | A fresh instance per batch ([Batch semantics](#batch-semantics)) |
| Batch composition | Per-row semantics with bisection ([Batch semantics](#batch-semantics)) |
| Stack depth | Fixed `max_wasm_stack`. Replicas of a cluster run the same binary on the same architecture, so the depth is the same everywhere. |

Fuel accounting and stack-overflow depth can differ between wasmtime
versions, so a row that runs out of fuel on one Materialize version might
succeed on the next. This is acceptable. Dataflows are rebuilt on restart,
and materialized view sinks correct their output against persist, so a
version change produces corrections rather than stuck retractions. It is the
same situation as a bug fix to a builtin function. During a zero-downtime
upgrade the new version runs in read-only mode until cutover, so the two
versions never write the same shard.

### Resource limits

| Limit | Mechanism | Default | Ceiling (system var) |
|---|---|---|---|
| Instructions per call | wasmtime fuel | 100M | `max_wasm_function_fuel` |
| Linear memory per instance | A `ResourceLimiter` that fails the call on growth past the limit | 64 MiB | `max_wasm_function_memory` |
| Module size | Checked when `CREATE FUNCTION` is sequenced | 8 MiB | `max_wasm_module_size` |
| Stack | `max_wasm_stack` | 512 KiB | none |

The ceilings are checked when a new function is created, not when its
statement is planned, so that lowering a ceiling never stops existing
functions from being re-planned at boot.

A limit applies to a whole call, not a row. That is what makes the
bisection argument work, so the defaults are sized for a full batch rather
than for one row: 100M fuel leaves about 6K instructions per row at the
default maximum of 16K rows, and the invoker sizes later batches of heavier
functions from the fuel recent calls used per row. 64 MiB covers the input
and output IPC buffers of an 8 MiB batch plus working memory. Fuel is
deterministic, so exhausting it is an ordinary deterministic error. We do
not use epoch interruption: it depends on wall-clock time, so it cannot be a
query error. Calibrating fuel against wall time, so that a call at the fuel
ceiling holds a worker for tens of milliseconds at most, is part of the
benchmarking work.

Instances use wasmtime's on-demand allocator with copy-on-write memory
images, not the pooling allocator. A pool has a fixed number of slots, and a
call that found the pool exhausted would fail for reasons unrelated to its
row, which is a nondeterministic error. Wasm memory is not tracked by the
replica's memory accounting. At 64 MiB per concurrent call the worst case is
small next to replica sizes, but the introspection work in
[Future work](#future-work) should report it.

### Catalog and planning

**Parser.** Add `Statement::CreateFunction` with the grammar above, parsed in
`parse_create`, and `SHOW [REDACTED] CREATE FUNCTION`. Add the keywords
`LANGUAGE`, `RETURNS`, `BASE64`, `IMMUTABLE`, `STABLE`, `VOLATILE`, `CALLED`,
`EXPORT` and `FUEL`. `DROP FUNCTION name` parses like other item drops, and
function names in `DROP` and `SHOW CREATE` resolve in the function namespace.

**Plan.** `plan_create_function` does the following:

1. Decodes the base64.
2. Parses the module with `wasmparser` (decode and validate only, no
   compilation).
3. Checks for an `ARROWUDF_VERSION_3_*` export.
4. Decodes every `arrowudf_*` export name into a signature.
5. Maps the SQL signature to an arrow-udf signature string using the
   type-mapping table and checks that the matching export exists. On a
   mismatch, the error lists the signatures the module does export.
6. Checks the import list against `wasi_snapshot_preview1`.
7. Computes the module's SHA-256.

environmentd never compiles or runs modules. `wasmparser` validation is
linear in module size and involves no codegen, so it is cheap to run on the
coordinator. It runs again at boot, when `create_sql` is re-planned.

**Catalog item.** `CatalogItem::Func` wraps a `Func` whose definition becomes
an enum, `FuncDef::Builtin(&'static mz_sql::func::Func)` or
`FuncDef::Wasm(WasmFunction)`. The WebAssembly arm holds the `create_sql`,
the resolved ids of the signature, and the planned `mz_sql::plan::WasmFunction`:
signature, null behavior, limits, hash, export name, and the decoded bytes as
`Arc<[u8]>`. `create_sql` round-trips through the existing
`CatalogItemV1 { create_sql }` durable shape, and the durable enums already
have `Func` variants, so no catalog migration is needed. Dependency tracking
mostly works already: name resolution records the function id in
`ResolvedIds`, so views that call it block `DROP ... RESTRICT`.
`CatalogItem::references` and `uses` need their `Func` arms filled in.

**Resolution.** `resolve_func` goes through `CatalogItem::func()`, which
returns `&'static Func`. User functions get a separate accessor, and
`plan_function` branches on it. A user function in a schema on the search
path follows normal Postgres resolution, with `pg_catalog` searched first
unless it appears explicitly in `search_path`.

**Expression.** A new `VariadicFunc::Wasm(WasmFunc)` variant:

```rust
pub struct WasmFunc {
    /// Fully qualified name at plan time. Used only for display and error
    /// messages.
    pub name: String,
    pub module: WasmModuleHash,
    /// The arrow-udf signature string, e.g. `gcd(int32,int32)->int32`.
    pub signature: String,
    pub arg_types: Vec<SqlScalarType>,
    pub return_type: SqlScalarType,
    pub strict: bool,
    pub limits: WasmLimits,
    /// Bound at render time. Not serialized, and not part of `Eq`, `Ord` or
    /// `Hash`.
    pub invoker: Option<Arc<dyn WasmInvoker>>,
}
```

It carries the hash, not the bytes, so plans, `EXPLAIN` output and the
LIR-stable format stay small. It follows the `Regex` precedent: `Hash`, `Eq`
and `Ord` cover the serialized fields only. The properties are:

- `could_error`: always true.
- `is_monotone`: false. Persist filter pushdown's abstract interpretation
  treats the result as unknown.
- `propagates_nulls`: equal to `strict`.
- `introduces_nulls`: true.
- `output_type`: the declared return type.

The new variant is added to the LIR schema snapshot and to the function
registry, with a `Sample`, as the pinned LIR design requires.

**No constant folding.** `MirScalarExpr::reduce` and `FoldConstants` evaluate
calls whose arguments are all literals, in environmentd. `reduce` skips
`Wasm` calls, and `FoldConstants` checks `contains_unfoldable`, which is true
for unmaterializable and `Wasm` calls alike. Unlike the unmaterializable
mechanism, this does not stop the expression from being rendered in a
dataflow. With no folding:

- `SELECT gcd(4, 6)` becomes a Map over a Constant. It plans as a slow-path
  peek and runs on the cluster, like any non-constant query.
- `INSERT ... VALUES (gcd(1, 2))` and `UPDATE ... SET a = gcd(a, b)` take the
  existing read-then-write path.

Other environmentd sites that evaluate constant expressions (LIMIT and OFFSET
planning) require literals after reduction, so a UDF there is rejected as
non-constant.

**Rejected contexts.** The rule is that a UDF may appear only where the
expression is rendered in a compute dataflow or a compute peek. Kafka sink
`PARTITION BY` (evaluated in storage) and webhook `CHECK` expressions
(evaluated in environmentd) reject `Wasm` calls at plan time. Column
`DEFAULT` expressions, temporal filter bounds and continual tasks still need
an audit against the rule.

### Module distribution

Clusters need the module bytes. A content-addressed compute command,
`ComputeCommand::InstallWasmModule { hash, bytes }`, delivers them:

- The coordinator registers a function's module with the compute controller
  when the function is created, when its creation arrives through a catalog
  update, and at bootstrap. Bootstrap visits catalog entries in dependency
  order, so a module is registered before any dataflow that calls it ships.
- The controller keeps every registered module, sends each to every existing
  instance once, and sends all of them to new instances when they are
  created.
- Commands to a replica are ordered, so a module always arrives before any
  `CreateDataflow` or `Peek` that references it. Command history compaction
  keeps each module once, ahead of the dataflows, so reconnecting replicas
  get them first too.

Dataflow descriptions and peeks carry only hashes, so neither changes shape,
and fast-path peeks need no special handling.

On the cluster, every worker receives the command, and the process-wide
runtime compiles each hash once into an `InstancePre` with the deterministic
WASI context linked: the first worker compiles and the others wait for its
result. A module that fails to compile on the cluster (it passed validation
in environmentd but hit a codegen limit) is recorded as failed, and every
call to a function that uses it fails with a deterministic error naming the
compile failure, rather than panicking.

### Storing the module

The bytes live base64-encoded in `create_sql`, in the durable catalog. That
is simple, keeps boot re-planning uniform, and makes `SHOW CREATE FUNCTION`
round-trip. It also means every catalog snapshot at boot carries every
module, which is why the size cap exists. A release-mode arrow-udf module
with arrow-rs linked in, after `wasm-tools strip`, is typically hundreds of
KB to a few MB, so 8 MiB leaves headroom. A separate blob store with a content
hash in `create_sql` is future work, and the hash-keyed design above does not
have to change for it.

`mz_catalog.mz_functions` gets a row per user function. `pack_func_update`
gains a user-function arm. `CREATE FUNCTION` is a sensitive statement kind,
so statement logging records its redacted form, in which the module is
`'<REDACTED>'`, and megabytes of base64 never land in
`mz_statement_history`. A `mz_internal.mz_wasm_functions` table exposing
`module_hash`, `module_size`, `signature`, `strict` and the limits is future
work. `mz udf create` and `mz udf pull` print the hash meanwhile.

### Logging

Output the guest writes to stdout and stderr cannot affect results, so it is
safe to capture. On a cluster it goes to the replica's tracing at `debug`
level, rate-limited per function, and in v1 users do not see it. In the CLI
it is printed inline. Local reproduction is the main way to debug a
function, and exposing guest output from clusters is future work.

### Developer experience

#### Building a function

The guest side is plain arrow-udf:

```sh
mz udf new gcd            # Cargo.toml with arrow-udf, crate-type = ["cdylib"], src/lib.rs
cargo build --release --target wasm32-wasip1
mz udf check target/wasm32-wasip1/release/gcd.wasm
```

```rust
use arrow_udf::function;

#[function("gcd(int, int) -> int")]
fn gcd(mut a: i32, mut b: i32) -> i32 {
    while b != 0 {
        (a, b) = (b, a % b);
    }
    a.abs()
}

#[function("safe_div(bigint, bigint) -> bigint")]
fn safe_div(a: i64, b: i64) -> Result<i64, String> {
    a.checked_div(b).ok_or_else(|| "division by zero".into())
}
```

The scaffold pins an arrow-udf version the host is tested against, sets
`panic = "abort"` and `opt-level = "s"`, and adds a `wasm-tools strip` step.

#### `mz udf`

All subcommands link `mz-wasm-udf`, so type mapping, the WASI context,
batching, bisection, fuel and memory accounting match the cluster exactly.
`FUNCTION` arguments name a guest function, or give its full signature when
the name is overloaded. SQL types come from the signature
(`UdfType::default_sql_type`), with lists presented as arrays.

Local, no connection needed:

- `mz udf check <module>`: validates the module and ABI version, prints its
  size and hash, lists every exported signature with the SQL signature it
  maps to (or why it cannot map), and warns about `random_get` and
  `clock_time_get`.
- `mz udf check <module> --determinism <function> --input cases.csv`: runs
  the input in one batch, one row per call, in batches of seven, and in
  reverse order, and reports every row whose outcome differs. This is the
  only check for the "row `i` depends only on input row `i`" contract, so
  the docs should make it part of the build.
- `mz udf sql <module> <function> [--name n] [--strict]`: prints a
  ready-to-run `CREATE FUNCTION` with the base64 inlined, for use from psql,
  dbt or `mz-deploy`.
- `mz udf call <module> <function> <args...>`: invokes the function with
  SQL-literal arguments or `NULL`. It prints the result or error, and on
  stderr the number of guest calls and bisections, fuel used, peak linear
  memory and captured output. Trap errors include the guest's panic message
  and a backtrace with name-section names.
- `mz udf call ... --input cases.csv`: the same for every row of a
  headerless CSV file, run through the batched path. `--fuel`, `--memory`
  and `--batch-rows` override the defaults.

Against a region:

- `mz udf create <module> <function> [--name n] [--schema s] [--strict]`:
  runs the generated `CREATE FUNCTION`, which avoids the psql base64 step
  entirely.
- `mz udf pull <name> [-o out.wasm]`: downloads the deployed module (from
  `SHOW CREATE FUNCTION`) and prints its hash, to confirm what is actually
  running.
- `mz udf replay <module> <function> --query 'SELECT a, b FROM t WHERE ...'`:
  runs a query in the region, feeds the result rows through the local
  runtime, and reports the rows that error, with their arguments. This is the
  answer to "my MV has a `gcd: trap` error, which input caused it?". Cluster
  errors deliberately omit argument values, which may be large or sensitive.

`mz` has no in-process Postgres client: it shells out to `psql`. The region
commands do too, sending SQL on stdin, because an 8 MiB module does not fit
in a command-line argument, and reading query results in `COPY ... TO
STDOUT` text format, which `mz_pgcopy` decodes into typed rows. `mz` is also
Cloud-only, since every connection goes through a Frontegg app password and
the Cloud region API. The local commands work anywhere.

`mz-deploy` already has a `tokio-postgres` client, host/port profiles and a
Docker sandbox. Whether the region commands belong there as well is an open
question. Profiling with wasmtime's `GuestProfiler`, which writes Firefox
Profiler files that show where fuel goes, is future work.

### Where the code goes

- `src/wasm-udf-abi` (`mz-wasm-udf-abi`): the guest contract without a
  runtime. Signature strings and their export-name encoding, the SQL to
  arrow-udf type mapping, the WASI preview1 function list, default limits,
  and `ModuleInfo::parse`, which validates a module with `wasmparser` alone.
  `mz_sql` uses it for `CREATE FUNCTION`, so environmentd does not link
  wasmtime.
- `src/wasm-udf` (`mz-wasm-udf`): the engine configuration, the
  deterministic WASI implementation, the Arrow IPC codec, single calls in
  fresh instances, the `WasmInvoker` implementation with bisection and batch
  sizing, and the process-wide module cache. It depends on `wasmtime`
  (Cranelift, on-demand allocator), `wasmparser` and `arrow` (already a
  workspace dependency; the IPC format is stable, so the host's arrow version
  is independent of the guest's). The license check (`deny.toml`,
  `about.toml`) needs Apache-2.0 WITH LLVM-exception, which the Bytecode
  Alliance crates use and which is already allowed. A guest fixture crate and
  its gzipped build live under `src/wasm-udf/tests/fixtures`.
- `src/expr`: `VariadicFunc::Wasm`, the `WasmInvoker` and `WasmRuntime`
  traits, `EvalError::WasmFunction`, the batched MFP evaluator, and the
  constant-folding guard.
- `src/compute`, `src/compute-client`, `src/compute-types`: the
  `InstallWasmModule` command, the batched render paths, and the batch-size
  dyncfgs.
- `src/sql-parser`, `src/sql`: grammar, planning, the feature flag and
  limits.
- `src/catalog`, `src/adapter`: the catalog item, builtin table rows, module
  registration with the compute controller.
- `src/mz`: `mz udf`.
- `src/environmentd/tests/wasm_udf.rs`: end-to-end tests over SQL, including
  a restart.

## Minimal Viable Prototype

The implementation is behind `enable_wasm_functions`, with a fixture guest
crate (`src/wasm-udf/tests/fixtures/udfs`) exercising every behavior the
runtime guarantees: per-row guest errors, traps, fuel and memory limits
attributed to rows by bisection, the deterministic WASI stubs, captured
output, a stateful guest that breaks the per-row contract, and a `batch_fn`
guest that receives ten thousand rows in one call. Planning, batched MFP
evaluation, and an end-to-end test over SQL (including a restart) cover the
rest.

The measurements still to take, which set the default batch size and limits:

1. A criterion benchmark of amortized per-row cost for `gcd`, a string
   function, and `saxpy` at batch sizes 1, 16, 128, 1024 and 16K, broken
   down into instantiation, IPC encode and decode, and guest time.
2. Fuel overhead (on versus off), fuel calibrated against wall time, and the
   cost of bisection for a function that traps on 1% of rows.
3. An MV over 10M rows with a UDF against the same MV with a builtin, and
   against the per-row fallback.

They also decide whether IPC file format is good enough or whether we
propose a faster transport upstream.

## Alternatives

**Component model with WIT types, row-at-a-time.** The first draft of this
design. Each SQL function is a typed WIT export, invoked once per row with
canonical-ABI lowering. It has self-describing signatures, and existing
tooling generates bindings for Rust, Go, C, Python and JS. We rejected it for
three reasons:

- It requires designing and maintaining a third SQL type mapping, in WIT,
  including every composite type, next to the Arrow mapping we already
  maintain.
- Row-at-a-time calls pay instantiation and call overhead per row, and
  keeping it low needs either instance reuse (a determinism risk) or
  micro-optimizing a path that batching amortizes anyway.
- It is incompatible with the RisingWave and Databend guest ecosystem.

The component model remains a candidate for a second ABI if Python or JS
guests become a priority. It could carry Arrow IPC through a typed transport
(`eval: func(batch: list<u8>) -> result<list<u8>, string>`), which would keep
the Arrow type boundary and the batched evaluator unchanged.

**Core module with a custom scalar ABI** (ScyllaDB style: fixed-width values
as Wasm scalars, variable-length ones as pointer and length). This has the
lowest per-call overhead but no batching, no ecosystem, and signatures that
are not self-describing. Rejected.

**arrow-udf-runtime as the host.** It would save host code, but it
configures no fuel, epoch or memory limit, reuses instances from a pool, uses
the legacy `wasi-common` crate with a real clock and random source, and has
no notion of per-row semantics under batching. The host is where Materialize's
guarantees live, so we write our own and share only the guest ABI.

**Evaluating UDFs in environmentd (allowing constant folding).** This would
put a Wasm runtime and untrusted code execution on the coordinator, and make
DDL and query planning latency depend on user code. Not folding costs little:
constant UDF calls are rare, and when they occur they run on a cluster like
any other query.

**Vectorizing MFP evaluation in general.** A columnar MFP evaluator would make
UDF batching fall out naturally, and would help builtins too. It is a much
larger project. The staged batched evaluator here is compatible with it: it
batches only at UDF call sites and leaves everything else per row.

## Open Questions

1. **Batch size and limits.** Are 16K rows, 8 MiB, 100M fuel and 64 MiB the
   right defaults? Benchmarks decide this.
2. **Nested calls.** Calls under `If` fall back to per-row evaluation. Is
   that good enough for v1, or do we batch the taken branch by partitioning
   rows on the condition first? Partitioning is correct because each row
   still evaluates exactly the branches it would per row, but it complicates
   the evaluator.
3. **CLI home.** `mz udf` lives in `mz`, as asked. `mz-deploy` has a
   `tokio-postgres` client, host/port profiles for self-managed regions, and
   a Docker sandbox in which a test command could run a real Materialize.
   Should project integration (functions as `.wasm` artifacts in an
   `mz-deploy` project) live there?
4. **ABI evolution.** Do we propose an `ARROWUDF_VERSION_3_1` upstream (IPC
   stream format, or C Data Interface input) if IPC file overhead shows up in
   profiles, or treat the ABI as frozen?
5. **Seeded randomness.** Is a deterministic `random_get` the right default,
   or should modules that import it be rejected unless the user opts in?
   Rejecting would break most Rust modules that use `HashMap`.
6. **Privileges.** Do we add a per-function `EXECUTE` privilege now, or later
   alongside other RBAC work? Postgres grants `EXECUTE` to `PUBLIC` by
   default, so adding it later is compatible.
7. **Overloads.** Catalog items are unique by name within a schema. Supporting
   overloaded user functions would mean making the name plus argument types
   the item's identity, which touches name resolution broadly.
8. **Sandbox review.** Guest code runs inside clusterd, which holds persist
   and cloud credentials. wasmtime's isolation has a strong record, but this
   needs a security review, including Spectre mitigations and a policy for
   wasmtime upgrades.

## Future work

- Table functions through arrow-udf's `->>` signatures and
  `record_batch_iterator_next`. We need to fix its dropped errors first,
  either upstream or by treating an iterator that ends early as a
  batch-level failure.
- Aggregates. arrow-udf has no aggregate ABI yet, and a differential-friendly
  one needs retraction support, which would be a new proposal.
- Per-replica introspection:
  `mz_internal.mz_wasm_function_statistics_per_worker` (calls, rows, batch
  sizes, bisections, errors, fuel, time, peak memory).
- A module blob store for large modules.
- Batching the taken branch of nested calls ([Open questions](#open-questions)).
- Batching the remaining per-row sites: `Reduce` key and value plans, MFPs
  after table functions, peek result iteration, and join closures (by
  lifting `Wasm` expressions out of closures at lowering).
- Keeping persist filter pushdown for source MFPs that call UDFs, by pushing
  down the part of the MFP that does not depend on a call.
- `mz_internal.mz_wasm_functions`, and evicting compiled modules no installed
  dataflow references.
- `mz udf profile`, demangled backtrace names, and DWARF symbolication in the
  CLI.
