# User-provided LIR plans: findings

* Rendering panics on several plan shapes the LIR types permit, and the validator rejects each of them: `Let` or `LetRec` outside the binding prefix that `RenderPlan::try_from` accepts (the controller panics with `valid plan`), `LetRec` id, value, and limit vectors of different lengths (`zip_eq`), `Union` strategies of a different length than its inputs (`zip_eq`), duplicate `LirId`s within a let-free plan (the node map loses a node), a repeated local id within one `LetRec` (`variables.remove(..).unwrap()`), an empty join equivalence class (`JoinClosure::apply` reads `exprs[0]`), and a top-k limit that references a column outside the group key (`permute_map` indexes a map of the group key).
* `DataflowDescription::depends_on`, which rendering calls for every export, panics on an export whose collection is neither an import nor a built object, and asserts that object ids are unique.
* An empty or error `Constant` has no arity, and the optimizer produces both, for example for `WHERE false` and for constant-folded errors. The validator treats them as producing no rows, skips the checks that need their arity, and takes the arity of an object whose output is empty from its index or sink export. Only an empty object without an export is rejected.
* Sinks may export an imported collection directly, and index export ids name a built object, not the indexed collection, because rendering looks up the arrangement to export at the index's own id.
* The arity of a `LetRec` binding is not stated in LIR. The validator reads it from the operators of the binding's value that state their output arity, iterated to a fixpoint across bindings, and rejects a binding where that finds none.
* `TableFunc::output_arity` overflows on a `WithOrdinality` around a `Wrap` or `CsvExtract` of width `usize::MAX`, so the validator uses a checked variant, `TableFunc::checked_output_arity`. `TableFunc::Wrap` with width 0 panics in evaluation (`chunks(0)`), which the function rules have to exclude.
* The check that envelope placeholders are `GlobalId::Transient` cannot live in `validate_dataflow`, because optimizer-produced dataflows use user and system ids. It belongs to envelope resolution.
