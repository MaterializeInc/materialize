# User-provided LIR plans: findings

* Rendering panics on several plan shapes the LIR types permit, and the validator rejects each of them: `Let` or `LetRec` outside the binding prefix that `RenderPlan::try_from` accepts (the controller panics with `valid plan`), `LetRec` id, value, and limit vectors of different lengths (`zip_eq`), `Union` strategies of a different length than its inputs (`zip_eq`), duplicate `LirId`s within a let-free plan (the node map loses a node), a repeated local id within one `LetRec` (`variables.remove(..).unwrap()`), an empty join equivalence class (`JoinClosure::apply` reads `exprs[0]`), and a top-k limit that references a column outside the group key (`permute_map` indexes a map of the group key).
* `DataflowDescription::depends_on`, which rendering calls for every export, panics on an export whose collection is neither an import nor a built object, and asserts that object ids are unique.
* An empty or error `Constant` has no arity, and the optimizer produces both, for example for `WHERE false` and for constant-folded errors. The validator treats them as producing no rows, skips the checks that need their arity, and takes the arity of an object whose output is empty from its index or sink export. An empty object without an export still flows to the objects that read it, as for `CREATE INDEX` on a view that folds to an empty constant, where `export_index` builds a separate `ArrangeBy` object at the index id. Only in user plans is an empty object without an export and without a reader rejected. The optimizer produces one for `EXPLAIN` of a peek that folds to an error, because it exports no index when explaining, and rendering needs no arity for it.
* Sinks may export an imported collection directly, and index export ids name a built object, not the indexed collection, because rendering looks up the arrangement to export at the index's own id.
* The arity of a `LetRec` binding is not stated in LIR. The validator reads it from the operators of the binding's value that state their output arity, following the bindings of `Let`s and `LetRec`s nested in the value, as the optimizer produces for nested `WITH MUTUALLY RECURSIVE`, iterated to a fixpoint across bindings, and rejects a binding where that finds none.
* `TableFunc::output_arity` overflows on a `WithOrdinality` around a `Wrap` or `CsvExtract` of width `usize::MAX`, so the validator uses a checked variant, `TableFunc::checked_output_arity`. `TableFunc::Wrap` with width 0 panics in evaluation (`chunks(0)`), which the function rules have to exclude.
* The check that envelope placeholders are `GlobalId::Transient` cannot live in `validate_dataflow`, because optimizer-produced dataflows use user and system ids. It belongs to envelope resolution.
* Rendering panics while building the dataflow when an operator reads a form its input's `CollectionBundle` lacks, whether or not the input has data: a `GetPlan::PassArrangements` key or raw collection the binding lacks, a `GetPlan::Arrangement` or `Collection` read, a keyed or raw `Mfp`, `FlatMap`, `Reduce`, and join source read, a join lookup, a `Threshold` arrangement, the raw input of `TopK`, `Negate`, `Union`, and every `LetRec` value, an `ArrangeBy` that must form the raw collection from an arranged-only input without an input key, an index export, and a sink without a raw collection or a matching `from_arrangement`. A node whose output has no form at all panics in the hydration logging every node gets (`CollectionBundle invariant`), and only `GetPlan::PassArrangements` can produce one. An `ArrangeBy` that forms an arrangement its input already has trips a soft assertion, which panics where soft assertions are enabled. The validator simulates the forms of every node and rejects each of these.
* Rendering never reads the permutation and thinning a plan states for an existing arrangement, it looks arrangements up by exact key equality. The physical layout comes from the producer, `ArrangeBy` forms and join stream thinnings, so the validator requires the triples of `ArrangeBy` and `Threshold` and every stream thinning to be the canonical ones of `permutation_for_arrangement`, which makes every arrangement's layout a function of its key and arity.
* A linear join without an initial closure streams an existing arrangement of its source by the first stage's stream key, whatever `source_key` says, and reads `source_key` only when there is none. The first stream thinning then has to be canonical over the source's arity rather than over the width `source_key` gives.
* Lowering states non-canonical triples in `Get` keys. When a residual MFP becomes the identity under an arrangement's permutation, lowering keeps that arrangement with an identity permutation and a trivial thinning (`lower_mir_expr`, after the operator match), and copies these into the `Get`s of bindings. For example, key `[#1]` over arity 3 with a residual projection `[1, 0, 2]` is stated as `([#1], [0, 1, 2], [0, 1])`, while the canonical triple has permutation `[1, 0, 2]` and thinning `[0, 2]`. Rendering ignores both for a `Get`, so the validator checks only their lengths there.
* An index import that excludes its snapshot provides its arrangement or a filtered raw collection, depending on the replica's `subscribe_snapshot_optimization` configuration. Sinks handle both, because they prefer the raw collection and otherwise read the arrangement lowering named. No other reader handles both, and the optimizer only excludes a snapshot when no built object reads the collection, so the validator treats such an import as providing nothing for certain to objects.
* Rendering translates index keys with `IndexDesc::as_lir`, which panics on functions that LIR cannot express, such as `mz_now()`. The validator rejects such import and export keys.
* The function allowlist for user plans has 23 entries: 16 scalar functions (`Not`, `IsNull`, `CastInt32ToInt64`, `CastInt64ToMzTimestamp`, `StepMzTimestamp`, `Eq`, `NotEq`, `Lt`, `Lte`, `Gt`, `Gte`, `AddInt64`, `SubInt64`, `MulInt64`, `And`, `Or`), one table function (`Wrap`, only with `width >= 1` and `width` declared types), and 6 aggregates (`Count`, `SumInt64`, `MaxInt64`, `MinInt64`, `Any`, `All`). An entry is admitted only after reading its body and the `eval` dispatch that reaches it, and confirming that inputs satisfying its typing rule cannot make either panic. Every other function is rejected with `Rule::Function`, so the excluded set is everything else in `UnaryFunc`, `BinaryFunc`, `VariadicFunc`, `TableFunc` and `AggregateFunc`.
* Functions defined with `#[sqlfunc]` over typed parameters do not panic on a datum of another type: `try_from_result` fails and the eager `eval` returns `EvalError::Internal("invalid input type")`. The panics sit in hand-written bodies and in bodies over bare `Datum` that call `unwrap_*`, for example `And` and `Or` (`unreachable!()` on a non-boolean), and in aggregate rendering (`datum_to_accumulator` panics on a non-boolean for `any`, and on a non-integer for integer sums).
* Function output types are not total either. `output_type` implementations unwrap their input types, for example with `unwrap_list_element_type`, so typing an ill-typed plan by output types can panic. Without the allowlist the validator catches such a panic and marks the column's type unknown.
* LIR constants carry no column types, so the validator infers them from datums. The optimizer produces constant columns the datums do not type: all-null columns, as for `SELECT NULL`, containers whose element type an empty or all-null container does not show, and strings, numerics and booleans that may be `jsonb`. Without the allowlist these columns have an unknown type. With it, all-null and container columns are rejected, and string, numeric and boolean datums take their non-JSON type, so a user plan cannot have a `jsonb` constant column of scalar datums.
* `TableFunc::Wrap` splits its arguments with `chunks(width)`. Besides `chunks(0)` panicking, an argument count that is not a multiple of `width` produces a short last row, which the `FlatMap` MFP then indexes past. A literal with no datum panics in `unpack_first`, and a temporal bound that is neither null nor an `mz_timestamp` panics in `MfpPlan::evaluate`.
* LIR states no column types for `LetRec` bindings. The validator visits the values repeatedly, starting from bindings no row reaches, until the binding types reach a fixpoint, and then checks the values once more against it.
* Source import operators are MIR expressions. The validator types them through their LIR translation, which fails on temporal filters (`mz_now()`), so such sources have unknown column types without the allowlist and are rejected with it. With the allowlist, keys that name an existing arrangement are typed like evaluated expressions, so a user plan cannot read an index whose key applies a function outside the allowlist.
* A reduce plan's variant has to match its aggregate functions: `finalize_accum` panics on an accumulable plan with an aggregate it does not accumulate, for example `MaxInt64`. The operator rules require every aggregate of a plan to have the reduction type (`reduction_type`) of its variant, which is the variant lowering picks for it.
* An accumulable reduce plan states each aggregate twice: once in `full_aggrs`, which rendering finalizes with, and once in `simple_aggrs` or `distinct_aggrs`, which rendering accumulates with (`datum_to_accumulator(&aggr.func, ..)`). The type rules check `full_aggrs`, so the validator requires every listed aggregate to equal the `full_aggrs` entry at its position, with the `distinct` flag matching its list, and the two lists to cover every position once. Otherwise a plan could type-check `count` and accumulate `dummy` or `any` over an `int8`, both of which panic. The other reduce variants state each aggregate once.
* `SingleBasicPlan::fused_unnest_list` makes rendering call `AggregateFunc::eval_with_unnest_list`, which asserts `can_fuse_with_unnest_list` and so panics for any aggregate other than the window functions lowering fuses. The flag also turns off the negative-multiplicity check. The operator rules reject the flag for any other aggregate.
* Constant rows carry arbitrary diffs, so a crafted constant can overflow the `count` and `sum` accumulators of a reduction. Overflow panics under `ore_overflowing_behavior=panic`, which CI uses, and soft-panics in production. The type rules do not bound diffs.
* Nested `LetRec`s multiply the visits of the values inside them, since each pass of an outer fixpoint reruns the inner ones. The validator charges its work to a budget and rejects a plan that needs more. Each operator visit is charged the serialized size of the operator without its inputs, constants by the encoded length of their rows, plus the width of its output, which bounds the copying and unification its parent does. Without these charges, a constant of many rows or a wide collection visited many times inside nested `LetRec`s costs orders of magnitude more than its visit count. Undoing the bookkeeping of a discarded visit costs work proportional to that visit. Column types are trees (records, lists, arrays, maps, ranges), and the rules clone, compare and unify them, so the width of an output is the total size of its column types. The validator treats a column type of more than 256 nodes as unknown, which bounds each such operation by a constant. In user plans it reports every such type where it arises (imports, literals, constants, and function output types), and rejects every function application and type check that meets an unknown type, since a typing rule cannot check what it does not know, and the allowlisted functions panic on datums of unexpected types. Without the allowlist, unknown types pass every check, as they do for all-null constant columns. Local bindings are looked up through a map from id to its bindings, since a `LetRec` binds all its ids at once and a linear scan per `Get` costs quadratic work in one pass. The budget is a constant plus a multiple of the plan's content, so a large plan passes and only amplification is rejected: the builtin `mz_catalog.mz_views` holds a constant of the generated builtin views' SQL and needs 686,000 units for a single pass, which a fixed budget of 1,000,000 would leave 1.5 times headroom for. Each binding takes its value's types as soon as the value is visited, so a chain of bindings where each reads an earlier one converges in a constant number of passes. A chain where each binding reads a later one, as `WITH MUTUALLY RECURSIVE` produces when each definition reads the next, needs one pass per binding, so the pass limit scales with the number of bindings.
* Rendering panics on several reduce and top-k plans the LIR types permit, and the operator rules reject each of them: a predicate in a reduce key or value plan (`Row expected as no predicate was used`), a zero bucket in a bucketed reduce or a basic top-k (each stage takes the hash modulo the bucket), a hierarchical reduce whose aggregate has no monoid (`get_monoid(..).expect`), a multiple basic reduce of fewer than two aggregates (a soft panic, and a panic for none), and a delta join path that reads its source raw from a relation other than 0 (`assert_eq!(source_relation, 0)` in `build_update_stream_stream`). Two soft assertions, which panic where soft assertions are enabled, are rejected too: a monotonic top-k with temporal bucketing that does not consolidate its input, and sink non-null assertions that are not strictly sorted. Source import operators that `MfpPlan::create_from` rejects, for example a temporal predicate it cannot express as a bound, panic in `render_dataflow` (`Linear operators should always be valid`) and are rejected as well.
* Lowering emits a bucketed hierarchical reduce without buckets when the expected group size is at most 16 (`bucketing_of_expected_group_size` starts at 16 and pushes only buckets below the limit). Rendering handles this: `build_bucketed` takes the first modulus as 1 and its final stage validates the input when no bucket stage did, so `err_output.expect` cannot fail. The builtin index `mz_wallclock_global_lag_recent_history_ind` has this shape and renders at every startup. The validator accepts bucketed reductions without buckets.
* Three render panic sites need no rule. The `TopK` stage error collection (`err_collection.expect` in `build_topk`) is always set, because the final stage validates whenever no bucket stage did. The source import MFP identity assertion in `render_dataflow` always holds, because `persist_source` takes the MFP and leaves the identity behind (`MfpPlan::take`). The delta join half-join closures (`Closure claimed to never error`) rely on `could_error`, which is accurate for well-typed expressions, and the type rules and the allowlist keep user plans well typed.
* Every recursive binding of a user plan must state an iteration limit, because rendering iterates a binding without one until it converges, and a recursion that never converges occupies the replica's workers indefinitely. Optimizer plans of `WITH MUTUALLY RECURSIVE` without `RETURN AT RECURSION LIMIT` have no limits, so the rule applies only with the function allowlist, which marks a user plan.
* Monotonic reduce and top-k variants turn every retraction that reaches them into an error in the output (`ensure_monotonic`), so the validator requires a monotonic input. The LIR analysis is the optimizer's logical `Monotonic` analysis per operator: imports marked monotonic, through `Get`, `Mfp` and `FlatMap` without temporal bounds or retracting table functions, `ArrangeBy`, joins and unions of monotonic inputs, distinct reductions and thresholds of a monotonic input, constants of positive diffs, and `Let` and `LetRec` bindings, where recursive bindings take the greatest fixpoint. It is stronger than the operator list in the design, which omits distinct reductions, thresholds and constants. Without them, optimizer plans of a monotonic top-k over a `DISTINCT` of a monotonic source would fail. Single-time dataflows also accept a physically monotonic input as `SingleTimeMonotonic` judges it, and, outside recursions, any input the operator consolidates, because lowering upgrades every hierarchical reduce and top-k there to a consolidating monotonic variant.
* Join plans whose paths do not cover their inputs render without panicking but compute another result. Rendering drops the matches of an input that no stage reads, and counts an update once for each delta path that starts at its relation. The validator requires a linear join's source and stages, and each delta path's source and stages, to read every input exactly once, and a delta join to have one path per input, path `i` starting at relation `i`. Lowering builds plans of this shape (`DeltaJoinPlan::create_from` adds one path per relation in order, and join orders cover the other inputs). The one exception is that `finalize_dataflow` keeps only the path from relation 0 of delta joins outside recursions in single-time dataflows, and the validator accepts that shape there.
* A source import's operators can hold temporal predicates, which retract rows as time passes. The validator therefore judges an import logically monotonic only if it is marked monotonic and the operators of none of its source imports have a temporal predicate.
* Inside a recursive value, logical monotonicity uses the greatest fixpoint over the bindings, as the optimizer's MIR analysis does. Within the iterations (`Product` timestamps), a binding judged monotonic can still carry retractions, so a monotonic operator inside a recursive value can report spurious errors (not panics), as the optimizer's plans for the same query would.
* `DataflowDescription::is_single_time` soft-asserts that the as-of is not beyond the until, so the validator checks that first and treats a dataflow that breaks it as not single-time.
* `test/sqllogictest/recursion_limit.slt` overflows the stack of a `tokio-rt-worker` thread in environmentd on its first query (388 `UNION`s), independent of this work. The overflow is in the derived `Clone` of the SQL AST (`SetExpr::clone`, recursing through `Box<SetExpr>`), called from `mz_adapter::frontend_peek::try_frontend_peek`, as a gdb backtrace on the crash shows. The same file and stack reproduce at d3b5806a06, which adds only design documents on top of upstream main, so the overflow predates the validator and the other changes for user-provided LIR plans.
* Extraction replaces each source import's pushed-down operators with a leading `Mfp` object over the raw import. It plans the MIR operators with `MapFilterProject::into_plan`, as rendering does, before translating them to LIR, because translating first fails on the `mz_now()` of temporal predicates, which planning turns into bounds. Every optimizer dataflow of the round-trip sweep (6146 SLT records, including TPC-H, LDBC BI, `WITH MUTUALLY RECURSIVE`, temporal filters, and every builtin index at startup) extracts, prints, parses, and maps back to its original objects, imports, and index imports, so the envelope needs no LIR form of source pushdown for correctness. It costs performance that was not measured: rendering passes the operators to `persist_source`, which reads only the columns they demand (`apply_demand`) and applies them while decoding, while an `Mfp` object sees full-width rows after decoding.
* A relation that has both a persist import with non-identity operators and index imports cannot be extracted, because a `Get` of the relation reads both and the pushdown object would hide the indexes. Extraction rejects it. The optimizer produced no such dataflow in the sweep.
* `envelope_to_json` writes rows without a readable form, for example intervals, as `StableRow`'s default byte-array serialization, and `parse_envelope` accepts that form, so such plans round trip. They are not writable by hand.
* The deepest optimizer envelope in the sweep nests 128 JSON levels for SLT queries and 107 for builtin indexes (`mz_internal.pg_type_all_databases_ind`). A chain of 400 views of `SELECT DISTINCT a + 1 ... WHERE`, built into one materialized view, nests 816 levels, against `MAX_JSON_DEPTH` of 4096. The optimizer rejects a chain of 800 such views with "exceeded recursion limit of 2048", so optimizer plans stay under the cap. The cap admits about 1360 nested single-input operators, fewer than the validator's recursion limit of 2048 operators, so the JSON depth, not the validator, bounds the depth of user plans.
* `mz_internal.mz_object_dependencies` derives the dependencies of user items from their `create_sql` (`collect_item_references` in `mz-sql-parser`), which sees only `[id AS name]` references in the AST. The imports of a `FROM PLAN` view live inside a string literal, so they are missing there, although the catalog records them as dependencies and dropping an import requires `CASCADE`. The `mz-deploy` dependency analysis, which visits the SQL query, misses them for the same reason.
* Only tables have relation versions in the SQL catalog interface (`CatalogItem::latest_version`). A materialized view's versions after a replacement are not visible there, and SQL references read its latest collection. Purification therefore records the root version for every non-table import, and planning reads such an import at its latest collection.
* The SQL type `char` without a length means `char(1)`, which carries a length modifier as much as `char(3)` does. `FROM PLAN` column definitions reject it with the other types with modifiers.
* mz-deploy cannot typecheck a `FROM PLAN` view whose imports are written as names, because it plans statements without purification and planning requires every import to be resolved to an item.
* The envelope of a user statement is parsed up to three times: by name resolution (to record resolved imports), by purification, and by planning. Each parse costs time proportional to the plan's size, which the prototype accepts.
* `ALTER MATERIALIZED VIEW ... APPLY REPLACEMENT` gives the target the replacement's item id and rewrites the ids in dependents' `create_sql` through the SQL AST (`create_stmt_replace_ids`). That visitor cannot see ids inside the plan string, so it parses the envelope of a `FROM PLAN` body, rewrites its resolved import ids, and prints it again. The name-based rewrites (`create_stmt_rename_refs`, `create_stmt_rename_schema_refs`) need no change, because purified plans name their imports by id.
