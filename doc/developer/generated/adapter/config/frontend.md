# adapter::config::frontend

Defines `SystemParameterFrontend`, which pulls `SynchronizedParameters` from either a LaunchDarkly SDK client or a local JSON config file, depending on `SystemParameterSyncClientConfig`.
The frontend maps LaunchDarkly feature-flag keys to system variable names using `key_map`, then updates the `SynchronizedParameters` set with fresh values on each `pull` call. For the file client, the config-sync file is read once per tick and cached in `config_file` (a `Mutex<Option<CachedConfigFile>>`); the cache avoids re-parsing and duplicate warnings when the file is unchanged between ticks. A parameter the file does not mention, and every parameter when the file is unreadable or unparseable, retains its current value. JSON `null` expresses no opinion for a parameter.
The `SystemParameterFrontendClient` enum encapsulates the two backend variants: `LaunchDarkly` (holding an `ld::Client` and an environment-wide `ld::Context`) and `File` (holding a path to a local JSON config file).
The LaunchDarkly transport is built by the private `ld_config` function via `mz_dyncfg_launchdarkly::https_transport`, which creates an HTTPS transport with a 10s connect timeout and a 300s read timeout (configurable via `MZ_LAUNCHDARKLY_READ_TIMEOUT`; the default exceeds LaunchDarkly's ~3-minute heartbeat interval to avoid spurious reconnects on idle streams). The transport auto-detects `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` environment variables. Two `MetricsTransport<T>` wrappers are applied: one around the event processor transport (recording the CSE Unix-second timestamp into `Metrics::last_cse_time_seconds`) and one around the streaming data source transport (recording the SSE timestamp into `Metrics::last_sse_time_seconds`). `MetricsTransport<T>` implements `HttpTransport` by forwarding to the inner transport and, on a successful response, updating a `UIntGauge` via a `NowFn`; the gauge is also updated on each body chunk so that a frozen timestamp on a long-lived SSE connection can trigger staleness alerts. When `base_uri` is provided, `ld::ServiceEndpointsBuilder::relay_proxy` redirects all SDK endpoints to that URL. The `ld_client` async function wraps initialization in a loop using `ld::Client::wait_for_initialization` with exponential backoff (starting at 5s, doubling up to 60s).
The LaunchDarkly context (`ld_ctx`) is a multi-context that registers `environment`, `organization`, and `build` contexts. For non-local environments the `environment` context carries the cloud provider, region, organization ID, and ordinal; for local environments anonymous contexts with fixed keys are used to avoid billable context proliferation. The `build` context carries the commit SHA and semver version. For scoped evaluation, `ld_ctx` accepts optional `cluster` and `replica` arguments that add the corresponding context kinds to the multi-context, enabling cluster-coherent and replica-local flag resolution.
`SystemParameterFrontend::from` handles the `base_uri` field from `SystemParameterSyncClientConfig::LaunchDarkly`, passing it to `ld_config` to redirect SDK endpoints.
`SystemParameterFrontend` exposes `pull_replica_overrides` and `pull_cluster_overrides` for scoped (per-replica and per-cluster) parameter evaluation. Both methods evaluate each object against LaunchDarkly using a context that includes a `cluster` or `replica` kind, compare the result against the environment-wide baseline via the private `evaluate_scoped_overrides`, and return a sparse map of overriding values. The difference test uses canonical encoding (so a boolean `"on"`/`"off"` environment-wide value is compared correctly against a raw `"true"`/`"false"` LaunchDarkly value). Unparseable values are silently dropped to prevent corrupt overrides reaching the optimizer. The file client returns an empty map for both scoped methods, as it has no notion of per-object evaluation.
`has_scoped_desired_state` returns `true` for the LaunchDarkly client unconditionally, and for the file client only when the most recent read succeeded and parsed as a JSON object. Callers use this to skip the scoped reconcile when the desired state is unknown, preventing accidental pruning of all overrides on a transient file-read failure.
`ClusterScopeContext` carries the cluster's catalog id, name, and `is_builtin` flag. `ReplicaScopeContext` additionally carries the replica's size, size family, and owning cluster linkage (id and name). `ClusterEvalContext` and `ReplicaEvalContext` bundle these scope contexts with their catalog IDs for use as inputs to the scoped evaluation pass.
