# adapter::coord::caught_up

Implements the "caught up" check used during zero-downtime deployments to determine when all collections have hydrated to a sufficient point before allowing the new environment to take over.
`Coordinator::spawn_caught_up_check_task` starts a background task that runs the check on an interval (`WITH_0DT_DEPLOYMENT_CAUGHT_UP_CHECK_INTERVAL`). Each tick, the task sends a `CaughtUpCheckRequest` to the coordinator via `Message::CaughtUpCheck`; `Coordinator::handle_caught_up_check_request` answers with a `CaughtUpSnapshot` carrying the coordinator's classification of every cluster. The task then applies the stability gate via `StabilityGate::ready`, which queries each caught-up replica's hydration times using `PeekClient::background_peek`. This split is necessary because the replica queries call back into the coordinator and would deadlock if run on the coordinator's main loop.
`CaughtUpCheckContext` holds per-collection exclusion state and the promotion trigger; it no longer carries per-cluster streak state. The `cluster_stability` field has been removed; stability is computed statelessly per tick by `observe_stability` from the replica health answers collected by the task.
The stability gate is implemented by `StabilityGate`, which holds a `PeekClient`. Its `ready` method queries each `Online` replica of every caught-up cluster using `background_peek` and `hydration_query`, then calls `observe_stability` with the resulting `ReplicaHealth` values. A replica that is `Online` and has logging enabled is asked (`ReplicaTarget::Ask`); one without logging is `Exempt` and does not block the gate; one that is not `Online` is `NotOnline` and immediately blocks.
`observe_stability` computes a `StabilityObservation` from a slice of `ReplicaHealth` values and the current wall-clock time. A cluster is stable since the latest of its replicas' `HealthySince` times, clamped to `now`. `StabilityBlocker` records the reason a cluster is held back: `NotOnline`, `NotHydrated`, or `WithinPeriod`.
The `ENABLE_0DT_CAUGHT_UP_STABILITY_CHECK` dyncfg controls whether the stability gate is enforced; `WITH_0DT_CAUGHT_UP_CHECK_STABILITY_PERIOD` sets the required stable duration.
For collections absent from the live-frontier snapshot (e.g. a table-to-MV conversion whose `GlobalId` remains a table on the leader), the caught-up check requires both full hydration and that the write frontier falls within the allowed lag of the current time — not merely that the write frontier is past the minimum. This prevents a fresh MV whose sink has advanced to frontier 1 after one batch from appearing caught up mid-hydration. There is no `cutoff` escape hatch on this path: a frontier frozen at the minimum blocks promotion until `with_0dt_deployment_max_wait` elapses.
