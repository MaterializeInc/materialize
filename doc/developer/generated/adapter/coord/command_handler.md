# adapter::coord::command_handler

Implements the coordinator's `handle_command` method, which dispatches each `Command` variant to the appropriate handler.
Covers session startup and teardown (`Startup`, `Terminate`), authentication, SQL execution (`Execute`, `Commit`), COPY FROM STDIN setup (`StartCopyFromStdin`), webhook lookup, system variable get/set, consistency checks, frontend-offload variants (`ExecuteSlowPathPeek`, `ExecuteSubscribe`, `ExecuteCopyTo`, `CopyToPreflight`, `ExecuteSideEffectingFunc`, `LookupConnection`, `RegisterFrontendPeek`, `UnregisterFrontendPeek`, `ExplainTimestamp`, `FrontendStatementLogging`) that reduce coordinator bottleneck, scoped feature-flag management (`UpdateScopedSystemParameters` dispatches to `Coordinator::reconcile_scoped_system_parameters`; `InstallScopedSystemParameterFrontend` stores the shared frontend into `Coordinator::scoped_frontend`), and the frontend read-then-write variants (`RegisterConnectionCancelWatch` installs a per-connection cancel watch channel; `CreateInternalSubscribe` delegates to `Coordinator::handle_create_internal_subscribe`; `AttemptWrite` delegates to `Coordinator::handle_attempt_write`; `DropInternalSubscribe` delegates to `Coordinator::drop_internal_subscribe`).
`LookupConnection` resolves a raw connection ID to its `ConnectionId` handle and authenticated `RoleId`, used by the frontend peek path to carry the target connection's handle while performing RBAC checks for `pg_cancel_backend`.
`handle_startup` performs privilege checks, triggers JWT group-to-role membership sync via `maybe_sync_jwt_groups`, sets session defaults, and emits the initial builtin-table writes for session tracking. The private `handle_startup_inner` encapsulates all fallible work: when it returns an error, no per-connection coordinator state exists (per-connection state is registered only in the `Ok` arm of `handle_startup`), so `handle_terminate` must not be called for a failed startup. Durable catalog changes made before an error (an auto-provisioned role, synced role memberships) are role-scoped rather than connection-scoped and are intentionally kept. `handle_terminate` must only be called for connections that completed a successful startup, i.e. that are present in `active_conns`; this is enforced by the coordinator's startup/teardown protocol and the cleanup guard in `Client::startup` that omits `Command::Terminate` on failure. During session default resolution, if the resolved `transaction_isolation` default names a feature-flagged isolation level whose flag is disabled (e.g. a role default set while `bounded staleness` was enabled, with the flag later turned off), that default is dropped so the session falls back to the built-in default.
At the start of each top-level statement execution (i.e. when `outer_context.is_none()`), the coordinator removes any pending cancellation watch for the connection via `connection_cancel_watches.remove`. This discards stale cancellations that arrived while no statement was running, preventing them from cancelling the next statement. Nested executes (e.g. FETCH executing its cursor's statement) skip this removal because the outer statement is still running.
For statements that cannot be run inside a transaction, the `OperationProhibitsTransaction` error redacts literals for sensitive statements (those where `StatementKind::from(&*stmt).is_sensitive()` is true) via `stmt.to_ast_string_redacted()`, preventing secret material from leaking into error messages that are persisted in `mz_statement_execution_history`. Other statements use `stmt.to_string()` for a clearer error.
`CheckRoleCanLogin` (`handle_role_can_login`) handles pre-authentication role existence and login-attribute checks; `InjectAuditEvents` inserts manually injected audit log entries via a catalog transaction.
A module-private `RoleLoginStatus` enum (`NotFound`, `CanLogin`, `NonLogin`) and `role_login_status` helper are shared among authentication handlers (`handle_authenticate_password`, `handle_generate_sasl_challenge`, `handle_authenticate_verify_sasl_proof`).
When handling `Command::DetermineRealTimeRecentTimestamp`, the RTR future is awaited via `Coordinator::await_real_time_recent_timestamp` so that `StorageError::RtrTimeout` and `StorageError::RtrDropFailure` are converted to humanized `AdapterError` variants before propagating.
