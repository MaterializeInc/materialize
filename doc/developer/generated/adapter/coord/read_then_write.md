# adapter::coord::read_then_write

Provides coordinator-side support machinery for read-then-write DML operations (INSERT, UPDATE, DELETE).

`DependencyPolicy` is an enum that governs which objects `validate_read_then_write_dependencies` accepts. `DependencyPolicy::UserDml` requires every relation leaf to be a writable user table (no system objects, no source-backed tables). `DependencyPolicy::SystemReads` accepts system objects across time domains, intended for coordinator-authored background work. Both policies reject `mz_now()` anywhere in the transitive dependencies.

`validate_read_then_write_dependencies` walks the transitive catalog dependency graph seeded by `ids: impl IntoIterator<Item = CatalogItemId>` and verifies that every reachable object satisfies the given `policy`. The traversal is iterative (worklist-based), not recursive, because dependency chains are user-controlled and can be arbitrarily deep; recursion would risk a stack overflow on the coordinator thread. A `seen` set deduplicates objects so diamond-shaped graphs are validated once per object. The traversal is bounded by `max_rw_dependencies: usize`; exceeding that limit returns `AdapterError::ReadThenWriteDependencyLimitExceeded { max_rw_dependencies }`.
Under `DependencyPolicy::UserDml`, an object is invalid if it is a source, secret, or connection; a non-user table (including system tables) or a source-backed table; or a system view or system materialized view. Under `DependencyPolicy::SystemReads`, an object is invalid if it is not a system object or not one of the supported item types (`Func`, `View`, `MaterializedView`, `Source`, `Table`, `Type`). Any view or materialized view whose optimized expression contains a call to `mz_now()` is rejected under both policies.
On failure, the function returns `AdapterError::Unsupported` (for `mz_now()` usage), `AdapterError::ReadThenWriteDependencyLimitExceeded` (when the dependency bound is exceeded), or `AdapterError::InvalidTableMutationSelection` with the offending object's name and type.

`Coordinator::handle_create_internal_subscribe` creates a subscribe that introspection does not see (`internal: true` on `ActiveSubscribe`). It accepts an `owner: ActiveSubscribeOwner` that identifies whether the subscribe belongs to a session or a coordinator background task; for `Background` owners there is no connection to check for cancellation. It takes ownership of `read_holds` and drops them only after the dataflow is shipped, preventing the `since` from advancing past `as_of` in the interim. The dataflow is shipped via `try_ship_dataflow` before the sink is registered, so a failure (e.g. a dependency dropped since optimization) leaves nothing to unwind. Results are delivered through a `response_tx` oneshot; if the receiver is gone when the handler runs, the internal subscribe is immediately retired via `drop_internal_subscribe`. `Coordinator::drop_internal_subscribe` cancels the dataflow on the compute side by delegating to `drop_compute_sink`.
`Coordinator::handle_attempt_write` enqueues a write attempt from the frontend read-then-write path or from coordinator background work. It accepts a `WriteAttemptKind`: `Session { conn_id, write_ts }` checks that the connection is still active before proceeding; `Background { write_ts }` bypasses the connection check. Both variants check that the coordinator is not in read-only mode and validate the target's current `GlobalId` generation against the caller's `target_global_id`; a generation mismatch sends `WriteResult::TargetChanged`. Background writes always supply a timestamp, so they always reach the `TimestampedWriteRequest` path; the group-commit blind-write path (`write_ts: None`) is reachable only from a session.
