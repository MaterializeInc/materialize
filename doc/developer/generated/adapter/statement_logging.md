# adapter::statement_logging

Implements sampled statement execution logging to the built-in `mz_statement_execution_history` and `mz_prepared_statement_history` catalog tables.
`StatementBeganExecutionRecord` and related structs capture the full context of a statement at the start and end of execution; the record includes an optional `kind: Option<StatementKind>` field used to redact `error_message` for statement kinds that can carry secret material. `StatementLifecycleEvent` enumerates the named milestones (optimization finished, storage/compute dependencies ready, execution finished) whose timestamps are tracked.
`PreparedStatementLoggingInfo::AlreadyLogged` carries a `kind: Option<StatementKind>` field alongside the `uuid`, so statement kind is available regardless of logging state. `PreparedStatementLoggingInfo::kind()` retrieves it uniformly from either variant. SQL text for sensitive statement kinds (those where `StatementKind::is_sensitive()` returns true, such as `CREATE SECRET`, `ALTER SECRET`, `INSERT`, `UPDATE`, and `EXECUTE`) is redacted via the `PreparedStatementLoggingInfo::still_to_log` constructor, which also stores a separately redacted copy in `redacted_sql`.
`StatementLoggingFrontend` bundles the statement logging state needed by the frontend peek sequencing path to log statements without holding a coordinator lock. It shares `throttling_state` and `reproducible_rng` with the coordinator's `StatementLogging`. Its `begin_statement_execution` method performs sampling, throttling, and record construction independently of the coordinator loop, returning a `StatementLoggingId`, the `StatementBeganExecutionRecord`, the pre-packed `mz_statement_execution_history` row, and an optional `PreparedStatementEvent`. `record_prepared_statement_as_logged` on the frontend mirrors the coordinator's method and transitions `PreparedStatementLoggingInfo` from `StillToLog` to `AlreadyLogged` once logging is committed.
`FrontendStatementLoggingEvent` is the enum of events the frontend peek path sends back to the coordinator: `BeganExecution`, `EndedExecution`, `SetCluster`, `SetTimestamp`, `SetTransientIndex`, and `Lifecycle`. The coordinator's `handle_frontend_statement_logging_event` dispatches these.
`WatchSetCreation` bundles the statement logging ID and transitive storage and compute dependency sets needed to install lifecycle watch sets. `WatchSetCreation::new` walks the transitive uses of an `CollectionIdBundle` from the catalog and categorises each item as a storage dependency (tables, sources) or a compute dependency (materialized views, indexes).
`ThrottlingState` implements a token-bucket rate limiter shared across the coordinator and all frontend tasks. `throttling_check` deducts the byte cost of a candidate log entry from the token pool (replenished at `statement_logging_target_data_rate` bytes per second, capped at `statement_logging_max_data_credit`) and returns whether the entry passes. `throttled_count` is a separate atomic tracking how many statements were throttled since the last successfully logged prepared statement; it is stamped into the prepared-statement row and reset on each successful log.
The free functions `effective_sample_rate` and `should_sample_statement` compute the Bernoulli sample rate (the minimum of the session var and the system max) and perform the sampling draw; `should_sample_statement` accepts an optional reproducible RNG for tests.
The private `serialize_params` helper uses `String::from_utf8_lossy` rather than panicking on non-UTF-8 bytes (which `"char"` / `PgLegacyChar` params can produce); when byte replacement occurs it logs a warning with the raw bytes in hex.
