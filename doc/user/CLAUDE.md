# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Scope: `doc/user/`, the Materialize user documentation. The repo-root `CLAUDE.md`
still applies (skills, commit conventions, prose style: no em-dashes).

## Commands

All paths below are relative to the repo root unless noted. Hugo commands run
from `doc/user`.

```bash
# Preview the site at localhost:1313 (from doc/user)
hugo server -D
hugo server --disableFastRender --ignoreCache   # when editing layouts/assets

# Build the markdown ("skill") output that ships alongside the HTML site
hugo --config config.toml,config.skill.toml --disableKinds sitemap,robotsTXT,taxonomy

# Full docs lint: builds BOTH outputs, then htmltest + catalog/metrics lints.
# Needs `brew install htmltest`. This is the CI gate for website deploys.
ci/test/lint-docs.sh

# Normalize markdown (trailing whitespace, final newline) across doc/user
bin/format-docs

# Pre-PR content review (uses .prompts/docs_pre_pr_review.md)
doc/user/docs-pre-pr-review-claude.sh --worktree | --staged | --range A..B | <files...>
```

CI builds with `hugo extended v0.152.2` (`ci/builder/Dockerfile`); locally a
newer extended build is fine, but Hugo template changes should be sanity-checked
against the pinned version when they use newer template functions.

### Regenerating checked-in artifacts

Do not hand-edit these; run the generator and commit the result.

| Artifact | Generator | Lint |
| --- | --- | --- |
| `data/metrics.yml` | `bin/gen-metrics-catalog` | `ci/test/lint-metrics-catalog.sh [--rewrite]` |
| `test/sqllogictest/autogenerated/mz_{internal,introspection,catalog}.slt` | derived from `content/reference/system-catalog/*.md` | `ci/test/lint-docs-catalog.sh [--rewrite]` |
| Chroma `mzsql` lexer | `bin/gen-chroma-syntax` (keywords from `src/sql-lexer/src/keywords.txt`) | — |

Editing a system-catalog reference page changes the generated `.slt` files, so
run `ci/test/lint-docs-catalog.sh --rewrite` and commit both. `data/sql_funcs.yml`
is the opposite: hand-maintained, and the source for all `content/sql/functions/`
pages, so new SQL functions must be added there manually.

## Architecture

Hugo site. `content/` markdown, `layouts/` templates and shortcodes, `data/`
YAML datastores, `assets/sass/` styles, `static/` images and fonts. `public/`
and `resources/` are build output and gitignored.

### Two output formats from one content tree

Every page renders twice: the HTML site, and a plain-markdown `skill` output
(`config.skill.toml` overlay → `public/markdown-docs/`) that is published next to
the site and consumed as agent-readable docs. The templates come in pairs:
`layouts/_default/single.html` / `single.skill.md`, and for shortcodes
`layouts/shortcodes/note.html` / `note.skill.md`.

**When adding or changing a shortcode that emits HTML, add the `.skill.md`
variant too.** Hugo falls back to the `.html` template when no `.skill.md`
exists, which leaks raw `<div>`s into the markdown output. Roughly two dozen
shortcodes currently lack a variant, which is a known gap, not a pattern to copy.

### Single-sourcing

Prose is shared rather than copied. Four mechanisms, all worth reaching for
before duplicating a paragraph:

- **`content/headless/`** — full markdown fragments. The section's `_index.md`
  cascades `render: never` and `headless: true`, so pages there never publish.
  Include with `{{% include-headless "/headless/path/to/fragment" %}}` — note the
  `{{% %}}` delimiters, since the fragment's own shortcodes must be rendered.
- **`data/*.yml`** — named prose entries (`- name:`, `content:`) pulled in with
  `{{< include-from-yaml data="file/path" name="entry" [field="content"] >}}`.
  Path is dot-free and slash-separated relative to `data/`.
- **`data/examples/*.yml`** — SQL syntax blocks and worked examples with
  `code`, `description`, `syntax_elements`, `results`, `addenda` keys, rendered by
  `{{< include-syntax file="examples/x" example="name" >}}` (syntax + element
  table) and `{{< include-example file="examples/x" example="name" >}}`.
- **`{{< yaml-table data="path" [columns="a,b"] [noHeader=true] >}}`** — tables
  from a `data/` file's `columns`/`rows` shape.

A broken `name=`/`example=` reference renders as *nothing*, silently, so verify
the entry exists in the target YAML after editing either side.

### Documenting unreleased features

Docs for a new feature merge in the same PR as the implementation. Gate them on
the release rather than holding the PR:

- `{{< warn-if-unreleased "v0.86" >}}` / `warn-if-unreleased-inline`
- `{{< if-released "v0.86" >}}` … `{{< if-unreleased "v0.86" >}}`
- `version-added: v0.86` on a `data/sql_funcs.yml` signature

These read `released:`, `date:`, and `patch:` from `content/releases/vX.Y.md`, so
the warning disappears on its own when that page flips `released: true`.
`{{< version >}}` expands to the latest released version. Content inside an
`if-released` block is invisible in PR previews; to check it, temporarily toggle
`released` in the release page.

Maturity callouts: `{{< public-preview >}}`, `{{< private-preview >}}`,
`{{< private-preview-inline >}}`.

### Navigation and links

Top-level sections and their identifiers live in `config.toml` under
`[[menu.main]]`; individual pages attach via front matter `menu.main.parent` /
`weight` / `identifier`. Renaming or moving a page requires an `aliases:` entry —
the deploy turns `#HUGOALIAS` markers into server-side S3 redirects
(`ci/deploy_website/website.sh`), so a missing alias is a hard 404 in production.

Use `mzsql` as the code-fence language for Materialize SQL. It is a real Chroma
lexer alias for the Materialize dialect; a typo like `mszql` silently drops
highlighting rather than erroring.

### Deploys

- Merge to `main` → live at materialize.com/docs immediately (`ci/deploy_website/website.sh`).
- PRs → `ci/test/preview-docs.sh` publishes preview.materialize.com/materialize/$PR.
- Branches named `self-managed-docs/*` publish a versioned snapshot to
  `/docs/self-managed/$VERSION` instead of the main site.

## Reviewing docs changes

The `docs-content-reviewer` agent and `.prompts/docs_pre_pr_review.md` encode the
content bar: technical accuracy, missing prerequisites and expected output, safety
risks in destructive examples, truncated sentences, headings that are vaguer or
broader than the content beneath them, verification steps that do not actually
prove the change took effect, cross-doc claims that exceed the reference page they
defer to, and broken include references. Prefer running that review over
freelancing a review of your own.
